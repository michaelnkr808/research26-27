## Next
1. **Seed-noise check before the full round** (presentation feedback, point 2; user chose 2026-11-03). Train the full-length D runs for training seeds 0 and 1 first, roll both out on the same episodes, and compare. If two seeds of the same config differ by about as much as the harm threshold (half the paper's D+R − D drop), 3 seeds can't settle the question; rethink seeds or N before training the other 13 runs. Costs no extra runs (both are among the 15); it only orders them. Started 2026-11-06: the rule is locked in the experiment PLAN "Seed-noise rule (locked 2026-11-06)", seed 1 trained 2026-11-06, seed 0 trained 2026-11-07 (experiment LOG 2026-11-07 (b)), both seeds' evals are submitted (experiment LOG 2026-11-07 (c)), and the rule is applied when both finish. No seed-noise comparison script exists yet: `lp_eval.py paired` compares two configs at one seed, so applying the locked rule needs new analysis code; when reading the shard files, glob `*of8.jsonl`, not `*.jsonl`, which would also catch `.errors.jsonl` files (reviewer's finding, verified from `src/lp_eval.py`).
2. **Fusion-step suspects test (conditional; user, 2026-11-06).** Runs only if the proxy replication (stage 4) finishes, calibration passes, and D+R vs D lands in the "proxy does not show a substantial effect" branch of the locked outcome rule. If the proxy does show the drop, the locked rule applies unchanged; if calibration fails, no fusion tests. The idea: the way channels from different encoders are combined may be why D+R hurts. Three suspects: (1) scale, one source dominating the concatenated vector (the paper says only "source-specific processing"; our proxy z-scores each channel, our choice); (2) double counting, C-RADIOv4 partly distilling DINOv3 (stated by the paper, Sec. 3.2 and 4.4; not tested by us) while each source's future-feature loss has weight 1.0; (3) grid mismatch, our proxy resizes C-RADIOv4's grid to the VAE grid, 14 x 14 per camera (our choice; the paper says features are aligned to the VAE latent grid, Sec. 3.3, but not how). The test would change our own choices where the paper is silent, one at a time, and see whether the D+R drop appears. Our choices may be hiding the drop we are trying to reproduce (speculative). The design is written later and goes to the user for sign-off before anything runs. Open questions and the evidence for each suspect: `writing/hypotheses-draft.md` "Update 2026-11-06: fusion-step suspects"; decision record: LOG 2026-11-06 [agent, planning].
3. **Cheap tests on perturbed frames** (presentation feedback, point 3; user chose 2026-11-03). The paper's drop is measured under LIBERO-Plus perturbations; our frozen-feature tests used clean frames only. Render matched clean/perturbed LIBERO-Plus frames (same scene and state, one perturbation category at a time), extract D, R, L, S, G features, and measure how far each encoder's features (and each D+B pair's) move under each perturbation. Check whether D+R stands out. No policy training. Caveat: only 4 partners to compare against the paper, so an ordering match is suggestive, not evidence. User decisions 2026-11-06: only the four picture types (camera, light, background, sensor noise); both measurements, with the action probe (trained on clean frames, tested on perturbed re-renders) as the main result and feature drift as a sanity check. Draft design, not signed off; the LIBERO-Plus source has been read and most design choices are made (user accepted the lead's picks, 2026-11-07): `experiments/2026-11-06-perturbed-frames/PLAN.md`. Waits until the proxy is trained (user, 2026-11-07): the design work can be finished meanwhile, but nothing is handed to the implementation session or run on the cluster before the proxy training finishes. Nothing runs before sign-off.
4. **Look at what happens between encoder layers, not just at the final output** (mentor, 2026-11-06; LOG 2026-11-06 [agent, docs] mentor meeting). The paper uses final-layer features only, with no layer study (paper note, 2026-11-06 section).
