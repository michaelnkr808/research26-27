## Question
Under the picture changes that LIBERO-Plus applies, does adding C-RADIOv4 (R) to DINOv3 (D) help less, or hurt more, than adding SigLIP 2 (L), SAM 3 (S) or VGGT-Ω (G)? The paper's D+R drop is measured under LIBERO-Plus perturbations (`literature/liu2026what-table10-composition.csv`; `../../README.md`, Key findings), while our frozen-feature tests used clean frames only (verified, `../2026-10-19-feasibility-tally/README.md`). On clean frames R adds the most action information on top of D (gain +0.037 vs +0.014 to +0.033 for the others; verified, tally README). This test asks whether that changes under perturbation.

Why look at the pair and not each encoder alone: C-RADIOv4 alone holds up about as well as DINOv3 in the paper's per-category Table 1 (camera 62.6 vs 64.2, light 97.3 vs 98.5, background 86.2 vs 83.9, noise 86.6 vs 86.0; verified, `literature/liu2026what-table1-single-source.csv`). The paper gives no per-category numbers for compositions (verified, paper note). So the harm, if it is visible at all in frozen features, has to show up in the pair.

## Proposed design (needs the user's OK)

### Frames: which data
Two candidates:
- **libero_goal HDF5** (`yifengzhu-hf/LIBERO-datasets`). The tally and diagnostics used it, so the clean probes, the demo-level split (100 test demos) and the cached D, L, R, S, G features already exist and the clean numbers are directly comparable (verified, `../../data/README.md` sections 1 and 4a). Images are 128x128.
- **Fast-WAM's `yuanty/LIBERO-fastwam`** (what the proxy round and the paper use). More faithful to the paper (512x512 frames, the paper's 1,712 episodes) but the frozen-feature probe results for it do not exist, and no D, L, R, S, G probe has been run on it (verified, data README sections 3 and 4b: only D, R and L caches exist there, no S or G).
- **Decided by the user (above): libero_goal HDF5**, same train/val/test split as the tally. The reasoning behind the recommendation: Reason: the whole test is a comparison against our own clean results, and S and G caches exist only for this data. Fidelity to the paper's data matters less here because no policy is trained.
- **Simulator states:** not settled by the repo for either dataset. The libero_goal contents list in the data README names images, actions, rewards and a language instruction per file, and does not mention simulator states. That list is incomplete, though: `src/diagnostics.py` (lines 87-88) reads `obs/joint_states` and `obs/gripper_states` from the same files, and the README line names neither. So a key missing from the README list proves nothing about the file (verified: the README line and the code were both read this session). Original LIBERO files are, from memory, supposed to carry per-step `states` and `robot_states` and a scene-file attribute (recalled, unverified). Fast-WAM's dataset lists images, an 8-d `observation.state` (end-effector pose 6 + gripper 2) and 7-d actions, and no simulator state (verified, proxy `PLAN.md` "Step 1 findings"). So this stays a feasibility question (below).

### Which demo moments
All frames of the 100 test demos (12,848 timesteps x 2 cameras = 25,696 frames per condition; verified, tally README, Config; the product is arithmetic). Training and validation stay on the clean stored frames, so nothing is re-rendered for them. Reason: the probe is trained on clean and tested on perturbed, as in the paper. (speculative: re-rendering train/val is not needed.)

### Conditions
Five test sets, same 100 demos in each: **clean re-render** (control), **camera**, **light**, **background**, **noise**. The clean re-render is the reference for "change under perturbation", so a perturbed-vs-clean gap cannot come from a difference between the stored images and our re-render. The pipeline check (do re-renders match the stored frames?) is done on train/val demos, not on the test demos, because the test set is touched only for final reporting (`_standards/07`). Proposal: render the clean re-render for a sample of val demos, compare images and compare the D probe's val R² on stored vs re-rendered frames. "Disagree" needs a tolerance set before looking. Proposed (not decided): the val R² of the D probe differs by more than 0.01, or the re-rendered frames differ visibly in orientation or scene content on inspection. 0.01 is a proposal chosen to be below the smallest clean gain in the tally (+0.014); the user sets it. If it fails, stop and find out why before anything is read. The tally's stored-clean test R² already exists (tally results), so no test-set use is needed for the stored reference; the re-rendered clean test is the main experiment's own control and is used once, in the final run.

### Perturbation settings per type
Use LIBERO-Plus's own sub-types and strengths, so "perturbed" means what the paper means (speculative as a choice). Sub-types as the lead read them through a summarizing fetch of the LIBERO-Plus paper (arXiv 2510.13626v3, Sec. 2.1 / App. A) and the repo README at `4976dc3` (**unverified; not read in primary text this session**):
- Camera: distance, spherical position (azimuth, elevation), orientation (yaw, pitch, roll); field of view per the README. The paper says only the viewpoint changes, "not the scene or robot state".
- Light: diffuse color, direction, specular, shadows on/off, reportedly through scene XML files.
- Background: scene theme textures and working-surface texture, reportedly through scene XML or new scene classes.
- Sensor noise: motion blur, Gaussian blur, zoom blur, fog, glass blur. Whether it is applied after rendering is not stated.

Sampling (proposal): one setting per (demo, type), drawn with a recorded seed and held fixed for every frame of that demo, because camera, light and background are properties of the scene, not of a frame. Sub-types uniformly, strengths from LIBERO-Plus's own difficulty levels where the source exposes them (`task_classification.json` carries a category and difficulty per episode; verified, proxy `PLAN.md` "Step 1 findings"). The exact parameter lists and ranges depend on the source check below; they get written into a config before any render and the config is the source of truth (`_standards/07`).

### Encoders
D plus R, L, S, G, with the same checkpoints and extraction settings as the tally (verified, `../../data/README.md` section 4a): DINOv3 `facebook/dinov3-vitl16-pretrain-lvd1689m` @ `ea8dc28`, 224 px, fp32; C-RADIOv4-SO400M (remote code `c0457f5`), 448 px, fp16 autocast; SigLIP 2 `google/siglip2-large-patch16-384`, 384 px (verified: `../2026-10-18-extract-libero-goal/job.yaml` line 60 passes `--variant google/siglip2-large-patch16-384`, and `../2026-10-18-extract-libero-goal/results/job.log` line 171 shows that hf_id); SAM 3 @ `3c879f3`, 1008 px, ViT backbone before the neck; VGGT-Ω @ `1041e80`, 512 px, final aggregator layer. Same rotate-180 handling, both cameras, global features primary and mean secondary (as in the tally). No reason to change anything (a changed setting would break the comparison with the cached clean features).

### Main measure: the probe
1. Fit as the tally does (`../../src/diagnostics.py`, verified), refit from the cached clean features with the alpha stored in the tally's result JSONs, because no fitted probe was saved: clean features, per-task-file demo-level split, ridge with alpha tuned on the clean validation demos, refit on train+val, R² on the test demos averaged over the 7 action dims, probes for D alone and D+B (concatenated, standardized with clean train statistics).
2. Apply the fitted probes, unchanged, to the test features of each condition. Alpha and standardization are never re-tuned on perturbed data (test data stays untouched in development, `_standards/07`).
3. Per condition c and probe X: R²_c(X). Define drop_c(X) = R²_clean-rerender(X) − R²_c(X).
4. Per-pair quantity: **extra drop** e_c(B) = drop_c(D+B) − drop_c(D). Positive means adding B makes the pair lose more under perturbation than DINOv3 alone. Equivalent forms: it is also minus the change in gain(B|D) from clean to perturbed. Report also gain_c(B|D) = R²_c(D+B) − R²_c(D) itself.
5. Pooled over types: e(B) = the mean of e_c(B) over the four perturbation types (each type weighted equally).
6. CIs: demo-level bootstrap over the 100 test demos, at least 1,000 draws, the same draws for every probe and condition so that differences between pairs are paired (as in the tally; `../../STANDARDS.md` requires demo-level CIs). The perturbation draw is fixed per demo, so its variation is part of the demo-level spread.

### Secondary measure: feature drift
Primary definition (proposal): for encoder E, drift_c(E) = mean over test frames of ||f(x') − f(x)||² divided by the mean over test frames of ||f(x) − mean(f)||², using clean-train standardized global features. Reads as "the fraction of how much this encoder's features normally vary between frames that the perturbation moves them". Dividing by the encoder's own spread is what makes it comparable across encoders with different feature sizes and scales. Single-encoder drift only; pair drift is dropped. With per-dimension standardization, the drift of a concatenation D+B comes out roughly as a dimension-weighted average of drift(D) and drift(B) (reasoning, not tested), so it adds nothing beyond the two single-encoder numbers. Same bootstrap over demos.
Alternatives: (a) 1 − cosine between f(x) and f(x'), divided by the median 1 − cosine between two different random frames of the same encoder; (b) linear CKA between the clean and perturbed feature matrices of the same encoder (scale-free, but a single number per encoder, so no demo-level CI without extra work). Drift is a sanity check: a feature can move a lot without moving the action-relevant part of it (speculative), so drift does not decide anything on its own.

### The "stands out" rule (decided by the user, 2026-11-06/07: P decides, B reported alongside, A not used)
**P (decides)**: D+R stands out if (i) e(R) is the largest of the four partners' e(B), and (ii) the lower end of the 95% paired-bootstrap CI of e(R) minus the next-largest e(B) is above 0.
Reported alongside, not deciding:
- **A**: not used (it was a looser per-type version of P; the user dropped it).
- **B (reported only)**: sign-based, on the level of the gain under perturbation. Pooled gain g(B) = the mean over the four types of gain_c(B|D). B fires if g(R) < 0 with the upper end of its 95% paired-bootstrap CI below 0, and g(B) is not below 0 for the other three partners, meaning each other partner's point estimate is at or above 0 (proposed reading; the CI-based reading is stricter). B tests the gain level under perturbation, which is closest to the paper's delta (D+B vs D under perturbation). P and A test the change from clean. They ask different questions, so they can disagree.
Also reported either way: the full ordering of the four pairs by e(B) beside the paper's ordering L (+1.83) > S (+0.49) > G (+0.40) > R (−5.41) (verified, tally README), with no significance claim. With 4 partners, "R is largest" has a 1 in 4 chance by chance (arithmetic). That figure covers only the ranking part: rule P also has its CI condition and rule B is a sign test, so their chance rates are not 1 in 4 and are not computed here. A hit is a hint (`../../PLAN.md` Next 3).
Note a mismatch to keep in mind: the paper's number per pair is closed-loop success under perturbation; ours is frame-level action regression from a linear probe. They differ in kind (`../../README.md`, Key findings).

### Caveat: probe capacity differs between pairs
The concatenated global probe input is 6,656-d for D+R, 6,144-d for D+G and 4,096-d for D+L and D+S (verified, tally README, Config). A larger e(R) could come partly from the bigger input (a higher-capacity linear probe may fall further when features shift), not from R as such. The tally pre-registered no matched-dimension control, and the direction `PLAN.md` Parked list has "Dimension-matched features in the frozen-feature tests". Decided by the user (2026-11-06/07): add a matched-dimension control, reported beside the full-size comparison, which stays primary (rule P is applied there). Proposal for the method, not decided: PCA of every encoder's clean features to one common size, fit on clean train frames only and applied unchanged to the other conditions; the common size is not fixed (it must be at most the smallest encoder's dimension, 1,024 per camera for the D, S and L globals per the tally README, Config, and is to be chosen before any result is seen). The same rules (P decides, B reported) are computed on the matched-dimension results and reported as a separate row.

### Predictions (speculative; for the user to confirm or change before running)
- All pairs lose some probe accuracy under perturbation (e_c(B) is defined relative to D alone, so this is about drop_c(D) > 0). Confidence: fairly high.
- If the paper's harm is visible in frozen features at all, e(R) is largest and rule P fires. Confidence: low. The clean tests showed R's gain at the top of the four, and the target-side test did not flag R either, so a null result (R does not stand out) is at least as likely.
- A competing guess: because R alone is as robust as D in the paper (background, noise slightly better), R's e(B) could be the smallest, not the largest.
- Drift: no confident prediction on the encoder ordering. Weak guess: G (a geometry encoder) moves most under camera changes.
Any of these coming out the other way is reported, not smoothed over.

### Sample size and CIs
100 test demos (verified, tally README; "10 task files x 10 test demos" is arithmetic from 50 demos per file x 20%), one perturbation draw per (demo, type). Demo-level bootstrap, at least 1,000 draws, paired across probes and conditions. Optional (needs OK, doubles render and extraction cost): two perturbation draws per (demo, type) to damp the draw-to-draw noise. With 4 pairs, no significance claim for the ordering (`../../STANDARDS.md`).

### Cost (rough; built only from costs recorded in the repo)
- Frames per condition: 25,696 (above). Five conditions. Raw RGB at 128x128x3 is about 1.3 GB per condition (arithmetic), so storage is small.
- Extraction time per condition from recorded rates: SAM 3 at 5.5 frames/s on a 2080 Ti is about 1.3 GPU-h; VGGT-Ω at 12.5 frames/s about 0.6 GPU-h (tally README); SigLIP 2-L at about 142 frames/s about 3 min and C-RADIOv4 at about 62 frames/s about 7 min, both measured on a TITAN RTX (extraction README). DINOv3 ran at about 66 frames/s in fp32 on a 2080 Ti (`../2026-10-19-feasibility-tally/results/extract-try2-job.log` lines 186-195; GPU named at line 8), about 0.11 GPU-h. Summed: about 2.1 GPU-h per condition and about 11 GPU-h for five (arithmetic from rates measured on different GPUs; speculative as a planning number).
- Probes and bootstrap: CPU. The tally's diagnostics ran about 23 to 45 minutes of wall clock per pair on 2 cores (per-pair `seconds` in `../2026-10-19-feasibility-tally/results/diag-*-job.log`: D+L 1374 s and D+R 1572 s, which together are the 49 min Job in the tally README; D+G 2690 s; D+S 1750 s). Here there is no CKA, but probes are refit and the bootstrap runs per condition, so the cost is not obviously lower (speculative).
- **Unknown:** the cost of re-rendering (depends on the feasibility answers below; simulator install per pod is part of it), and the analysis code, which does not exist yet. Probe reuse is settled by reading the code (verified, `src/diagnostics.py` lines 176-197): `ridge_select` returns predictions and discards the weights, and the test predictions are "kept out of the JSON" (line 194). So the JSON holds neither weights nor predictions, and no fitted clean probe exists to apply to new features. The analysis therefore needs new code: refit each probe from the cached clean features with the alpha stored in the tally's result JSONs, apply it to each condition's features, and save per-demo predictions or per-demo sufficient statistics for every condition and probe, so that rules P, A and B and the bootstrap can be recomputed later without refitting.

### Compute and gates
`../../STANDARDS.md` rules apply: Jobs that run a command and exit, never `sleep infinity`, start on 1 GPU, GPU utilization above 40%, requests and limits within 20%. Gate (stop and ask): more than 8 GPUs at once or more than 20 Jobs. 5 encoders x 5 conditions is 25 combinations, so extraction must be batched (for example one Job per encoder looping over the conditions, 5 extraction Jobs plus 1 render Job) to stay well under 20. The user's OK is needed before preparing or submitting any Job. Check GPU utilization about 15 minutes into the first extraction Job.
