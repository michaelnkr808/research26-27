The estimate multiplies the pilot's measured seconds per frame for each drawn noise code by 127.5 frames per demo (12,748 / 100) and adds the base render cost; for a code the pilot did not draw it uses the mean of the pilot's codes of the same family, and if the family has no measured code it uses the largest measured cost and says so (the pilot drew no zoom code, 21 to 30, so any zoom draw is priced pessimistically). The real frame count per demo differs from 127.5, so the estimate is approximate; the suggested cap is 1.5x the estimate plus 20 minutes. A cap that is too small makes the noise render fail with exit 124 and loses only the noise condition (the other four are already published and extracted).

## 4. Order, stagger and the stage order inside the render Job (shared cap: 8 GPUs at once in the namespace)

Recount the live GPU pods immediately before every submission; the plan below holds only if the number is true then.

4. **When the noise condition is published**: submit `job-pfb-ext-sam3-noise` and `job-pfb-ext-vggt` (VGGT needs all five markers). The twin carries the same `SRC_GIT_COMMIT` and the same `NOISE_CAP=10800` as the running copy's rendered manifest `jobs/rendered/job-pfb-render.yaml` (its env line reads `a3777d7db734bf1a7275df17b0e5f4ae57e90c84`; its script line reads `NOISE_CAP=10800`; re-read both before rendering). Render with the NOISE_CAP expression first (section 3), check the two lines in the rendered copy, then apply:
   `sed -e "s/NOISE_CAP=FILL_AT_SUBMIT/NOISE_CAP=10800/" -e "s/FILL_AT_SUBMIT/<sha>/" jobs/job-pfb-render-a6000.yaml > jobs/rendered/job-pfb-render-a6000.yaml`
   `grep -n "NOISE_CAP=\|SRC_GIT_COMMIT" jobs/rendered/job-pfb-render-a6000.yaml`
   `kubectl apply -f jobs/rendered/job-pfb-render-a6000.yaml`
2. When either pod gets a node, look at the other Job's pod: it must still have no `spec.nodeName` and no `status.startTime` (a pod that has started pulling the image or running the script has both). Only then delete the other Job (`kubectl delete job <name> -n aria-world`) and confirm no pod of it is left (`kubectl get pods -n aria-world`). If both pods already have a node, do not let both run: see the end of step 3.
3. The two Jobs must never both run. They write the same paths on the volume on purpose (`$PB/render/<c>`, `$PB/feats/<c>`, `reports/pfb-render-<stamp>`, logs), so the downstream SAM 3, VGGT and final Jobs need no change. The script refuses an existing output (exit 14 for a render folder or `.part`, exit 22 for an incomplete feature folder), which only catches a late second pod after the first has published, not two pods publishing at the same moment. There is no lock: the scripts are byte-identical on purpose and the original is already submitted. The window is narrow in practice (reviewer finding, kept as a known limit): a pod's first write to a shared path is its own timestamped log and then, after about 15 minutes of setup (section 6, speculative), the first render publish, so if both pods are found scheduled, delete the one that started later at once (`kubectl delete job <name> -n aria-world`; the user's OK to delete the loser is already given) and check `$PB/render/` and `$PB/feats/` for anything the deleted pod wrote before keeping the survivor's run.
4. Keep the winner's rendered manifest in `jobs/rendered/` and record in the LOG which Job lost.

**Risks.**
- *Storage across regions.* The PVC `stacking-encoders-proxy` is on `rook-cephfs`, the US West class (`experiments/2026-10-27-proxy-calibration/jobs/pvc-proxy.yaml`; `_standards/08`: "pick storage and compute in the same region"). A pod in us-central mounts it over the wide-area network; how much slower is unknown (speculative). Places that read or write the volume, with their caps (sized from phase-A rates in us-west, section 6): the log (`tee` to `/mnt/proxy/logs`, every line, no cap); the free-space check; the env bundle tar's sha256 (`cap 1800`) and the bundle restore (reads the tar, no cap); the phase-A render read by the consistency check inside each render stage (clean, camera, light, background `cap 3600` each; noise `NOISE_CAP` = 10800); `publish_render` (about 1.3 GB written per condition, read back by `sha256sum -c`, `cap 1800` each); `copy_feats` (feature files copied and compared byte for byte by reading them back, `cap 3600` per encoder and condition); the final report copy (no cap). The extraction itself reads local disk only (staged at `/work/pfb-test-<c>`), and the raw demos come from Hugging Face, not the volume. A stage that runs out of time exits 124, the Job continues and ends with the worst code. A publish or copy timeout loses that condition or encoder only; a leftover `.part` or `.partial` then blocks a retry (exit 14 or 22) until it is deleted by hand with the user's OK (`_standards/05`).
- *Render consistency check on a different card or driver.* Phase A's render ran on an L4 (`nautilus-it-gpu05`, driver 615.71.09; LOG 2026-11-09, `results/pf-main/phase-a/pfa-render-20261109-080327/pod-log.txt`). The check (PLAN Amendment 2026-11-09 (b) and (d)) re-renders demo_30 of each task and compares the uint8 pixels: an array passes if every differing value is off by at most 1 of 255 and fewer than 1 in 100,000 values differ (`MAX_ABS_DIFF_TOL = 1`, `FRACTION_TOL = 1e-5`, `src/pf_render.py:526-527`). GPU name, driver and GL strings differing are only recorded; library versions, the image digest, `MUJOCO_GL`, the bundle and the config hash must match, and they are the same in the twin. If an A6000 draws a wrist image that differs by more than that, `pf_rerender.py render --split test` stops with exit 5 before any test frame is drawn: `render-clean` shows exit code 5, `GO` becomes 0, nothing else is rendered or extracted, and the Job ends with exit 5 (the user then decides). Two L4 runs already differed by one step in about 1 in a million wrist values (LOG 2026-11-09), so some card dependence exists; an A6000 is untested (speculative).
- *40% GPU rule.* NRP judges hours-long GPU averages per card; a 48 GB card does not change that (`_standards/08`). The arithmetic of section 6 applies unchanged: setup and rendering are GPU-light, extraction is busy, the noise render adds idle time.
- *Other places that could depend on the card (read from the script; nothing found that changes results).* `nvidia-smi -L` is only printed; the batch size is fixed at 64 for all three encoders, not set from card memory (48 GB against 24 GB adds no out-of-memory risk); the stage caps are not per card (the extraction caps 1800, 1800 and 3600 s were sized for an L4, an A6000 is probably faster, speculative); the script has no region test; `JOB=pfb-render` is a fixed variable for log and report paths, not the Kubernetes Job name, so the twin writes `pfb-render-<stamp>` paths like the original. Feature values from a different card can differ at float rounding level (speculative).
