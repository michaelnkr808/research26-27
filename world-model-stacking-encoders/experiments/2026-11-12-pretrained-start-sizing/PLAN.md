# Plan: sizing check for a pretrained-start world action model (8 of 30 Wan 2.2 layers)

Written 2026-11-12 by an agent (planning worker) as a design for the user to sign off. Design only: no code, no Job or pod file, nothing run, no cluster or paid-compute action, nothing downloaded. Claims are labelled verified (checked against the file named), recalled (from memory, not checked here), or speculative (reasoning or arithmetic not yet measured). Predictions are speculative by definition. Once the check starts, this design is locked and changes become dated amendments at the bottom (`../../../_standards/04`). Paths are relative to `world-model-stacking-encoders/`.

## In plain words
Before any real training run on the pretrained Wan 2.2 video transformer, the user needs to know what one run costs. This check builds the model the way a real run would (Fast-WAM's joint model, cut to 8 layers, Wan 2.2 weights loaded, input layer widened for an encoder's features), feeds it a few real cached LIBERO batches, and times it. What comes out is a price tag and a list of cards the model fits on. It says nothing about whether the pretrained start or any encoder helps.

Background (verified, direction `LOG.md` entry "2026-11-12 [agent, lead, planning]"): the from-scratch 8-layer proxy (`src/proxy_wam.py`) scored far below the paper; the user decided on 2026-11-11/12 to start from the pretrained Wan 2.2 video transformer, at 8 layers first as the mentor suggested; Fast-WAM at commit `7faa711` loads `Wan-AI/Wan2.2-TI2V-5B`; the lead's cost arithmetic for an 8-layer run was "over a hundred card-hours", explicitly not measured for a truncated model. This check replaces that arithmetic with a measurement.

## Question
Can Fast-WAM's joint model (`FastWAMJoint`: Wan video expert plus action expert in a mixture of transformers), cut to 8 of its 30 layers and loaded with the `Wan-AI/Wan2.2-TI2V-5B` weights, with the input projection widened for extra encoder channels, load and take training steps on one card, and what does a step cost in peak GPU memory and in seconds?

## Design

### What is built
- **Model.** `FastWAMJoint` from Fast-WAM `7faa711`, built as the proxy builds it (`src/proxy_wam.py` `build_model`, lines 372-387, verified) but at the full Wan 2.2 TI2V-5B width instead of the proxy's 384: video expert width, FFN size, head count and head size, text dimension 4096 and frequency dimension 256 (`src/proxy_wam.py` line 68, verified) and patch (1, 2, 2) (line 65, verified) as in Fast-WAM's own config for this checkpoint; action expert at Fast-WAM's own width (the proxy keeps the paper's 3:1 video-to-action ratio, `experiments/2026-10-27-proxy-calibration/PLAN.md` line 129, verified). The proxy's code comment gives Fast-WAM's FFN ratio as 14336/3072 (`src/proxy_wam.py` line 373, verified), which suggests width 3072 and FFN 14336; the implementation session takes the exact numbers from Fast-WAM's config at `7faa711`, not from this sentence. Both experts get 8 layers (the proxy builds both with the same `layers`, line 383, verified; whether `MoT` requires equal depth is recalled, not checked).
- **Inputs, as the proxy feeds them:** cached Wan 2.2 VAE latents (48 channels on a 14 x 28 grid, 3 latent steps, 294 video tokens; proxy PLAN line 121, verified), cached umT5-XXL context (128 tokens, `src/t5_cache.py` line 22, verified) plus one proprio token, 32-step action chunks (`src/proxy_wam.py` line 60, verified); no VAE and no T5 inside the step (`LatentsOnly`, `src/proxy_wam.py` lines 366-369, verified). Extra encoder features are channel-concatenated per grid cell, [VAE 48 | source], and the patch embedding and output head are widened to match (proxy design, PLAN line 129, verified).
- **Training recipe, as the proxy's:** fp32 weights with bf16 autocast, AdamW (lr 1e-4, betas 0.9/0.95, weight decay 0.01), grad clip 1.0, Fast-WAM's loss with the video term split per source (`src/proxy_wam.py` lines 396-427, 474-502, verified). This precision choice sets most of the memory; see Open item 4.
- **Two configurations:** `none` (input 48 channels) and one extra encoder (input 48 + that encoder's channels; DINOv3 is 1,024, C-RADIOv4 and SigLIP 2 are 1,152, `data/README.md` lines 71-73, verified). Which encoder is Open item 3.

### Step 4: load and report (both configurations)
Build the 8-layer model, load the Wan 2.2 weights into the kept blocks, and write to `results/load-<config>.json`:
- every parameter name of the built model, tagged `loaded` (with the source tensor name), `new` (newly initialised) or `partly loaded` (the widened patch embedding and head: the 48 VAE-channel slice loaded, extra-channel slice new);
- every checkpoint tensor not used, tagged `skipped` (the 22 dropped blocks are expected here; anything else is listed and explained);
- counts of parameters in each tag, total and trainable;
- for every `loaded` tensor, a check that it equals the source tensor (max absolute difference 0, after any dtype cast that Fast-WAM's own loader applies);
- how the `new` and `partly loaded` parameters were initialised (Open item 5; the cost does not depend on it).

### Step 5: sanity items (`../../../_standards/07`, sanity checks)
On the first batch of each configuration, before timing, print and save to `results/sanity-<config>.json`:
- **Inputs inspected:** shapes and dtypes of every tensor fed to the model; per-channel mean and std of the VAE channels and of the z-scored source channels (source channels should sit near 0 and 1 on the slice); action and proprio ranges (inside [-1, 1] apart from clamped outliers up to plus or minus 5, `src/proxy_wam.py` lines 78 and 91, verified); counts of padded action steps and padded latent steps; the task strings of the batch. The frames behind these caches were already checked upright by eye (proxy PLAN line 122, verified), so no image is decoded here.
- **Loss at start:** the total loss and each part (video VAE channels, video source channels, action) at step 0, and the same parts for a zero prediction on the same batch and the same noise draws (the "predict zero" baseline). Expected: finite, and of the same order as the zero baseline (speculative, see Predictions). A NaN or infinite loss stops the check.
- **One overfit run is not part of this check.** It belongs to the first real run's plan (the direction's "clean training and clean testing" step, `LOG.md` 2026-11-12), which writes its own pass bar.

### Step 6: measurement
**Process isolation.** Every micro-batch size m, and the full-optimizer-step run, is its own fresh Python process. Reasons: the 2026-10-16 benchmark crashed when the batch size changed inside one process (`experiments/2026-10-16-fastwam-step-bench/README.md` line 62, verified), whether any part of Fast-WAM's joint model is compiled is not known here (Step 2), and after an out-of-memory a process keeps a fragmented allocator, so nothing measured after it in the same process is trusted. Each process classifies how it ended: `ok`, `oom` (only `torch.cuda.OutOfMemoryError`), or `error` with the exception type and message (for example a shape mismatch or a compiled-core error). Only `oom` ends the sweep as "does not fit"; an `error` stops the sweep and is reported as an error, never as a memory limit. To keep the extra loads short, the first process saves the built and loaded 8-layer state dict (with the AdamW states after one update) to local disk, and later processes load that file instead of re-reading the full checkpoint.
- **Micro-batch sweep, ascending:** micro-batch m = 1, 2, 4, 8, 16, 32, 64, 128, one process per m, stopping at the first `oom` or `error`. In each process, before any measurement, one full optimizer step at that m (forward, backward, gradient clipping, AdamW update) allocates the AdamW states (or loads them from the saved file), and the gradient buffers are then zeroed but kept (`zero_grad(set_to_none=False)`), so every peak below includes weights, gradients and both AdamW moments. Then empty the cache and reset peak memory stats, 3 warm-up micro-steps (forward and backward), then 10 timed micro-steps with `torch.cuda.synchronize()` around each. Record median and spread of seconds per micro-step, seconds per sample, `torch.cuda.max_memory_allocated` and `max_memory_reserved` after warm-up, and `nvidia-smi` used memory once per m.
- **Full optimizer steps at the proxy's batch:** global batch 128 (`src/proxy_wam.py` line 530, verified), built as 128 / m* accumulated micro-batches, in a fresh process started after the sweep (never after an out-of-memory in the same process), where m* is the largest power of two whose sweep `max_memory_reserved` is at most 0.9 x M, the same figure and the same M as the fit list in "Decision rule" (M = the card's reported total memory, `torch.cuda.get_device_properties(0).total_memory`). 1 warm-up optimizer step, then 2 timed ones, each including gradient clipping and the AdamW update. Record seconds per optimizer step and peak `max_memory_reserved` (this peak also covers the update's own temporary buffers, which the micro-step sweep does not; the fit list uses the larger of the two at m*). If this run ends in `oom`, it is repeated once in a fresh process at m*/2, and both outcomes are reported.
- **Data time kept separate:** batches for the whole check are assembled once into host memory before timing, so the step time is GPU time only. Host assembly time per batch is logged separately (the paid machine's disk is not CephFS, so it does not transfer to Nautilus).
- **Written to `results/`:** `measure-<config>.json` with the sweep rows (each with its process outcome `ok`, `oom` or `error`), the optimizer-step times, card name and reported total memory, driver, CUDA and PyTorch versions, Fast-WAM commit, this repo's commit, the layer indices kept, the encoder, the seed, and wall-clock time of each phase; the raw process log as `results/run.log`. A failed or killed run keeps its log and is noted in `LOG.md`, not deleted (`../../../_standards/07`, tracking).

## Predictions
Written before running. All speculative. The only measured source is the 2026-10-16 one-card benchmark: full 30-layer Fast-WAM, random weights, synthetic batch, forward and backward only, no optimizer step, RTX A6000, two points (`experiments/2026-10-16-fastwam-step-bench/README.md` lines 55-61, verified): micro-batch 1 took 0.808 s with 23.9 GiB peak, micro-batch 2 took 1.525 s with 29.0 GiB peak; VAE encode inside the step was 0.251 s and 0.479 s; 6.021B trainable parameters, 12.5 GiB of resident bf16 weights; about 5.1 GiB more per extra sample (README line 66, derived there).

1. **Loading.** The 8 kept video blocks, the text and time embeddings, the norms and the 48-channel slice of the patch embedding and head load with matching shapes; the 22 dropped blocks are skipped; the extra-channel slices, the proprio encoder and (unless Fast-WAM's loader or a published LIBERO checkpoint supplies it) the whole action expert are new. Source: the proxy's model structure (`src/proxy_wam.py` lines 372-387) and the 2026-10-16 trainable set "MoT (video + action experts) + proprio" (bench README line 8).
2. **Trainable parameters:** about 1.6B to 1.9B. Source: 8/30 of 6.021B is 1.61B; parts that do not scale with depth (embeddings, head, proprio encoder) add an unknown amount.
3. **Static memory (weights, gradients, AdamW states) under the proxy's fp32 recipe:** about 16 bytes per parameter (4 weights, 4 gradients, 8 AdamW moments), so about 24 to 28 GiB. Source: arithmetic on prediction 2. These 16 bytes leave out the bf16 copies of the weights that autocast may keep during forward and backward (about 2 bytes per parameter, so roughly 3 GiB more; the PR #27 review's figure, recalled, not checked here), so the static part could be about 24 to 32 GiB. With bf16 weights and gradients instead it would be lower (Open item 4).
4. **Activation memory per sample:** between about 0.45 and 1.4 GiB. Source: 5.1 GiB per sample x 8/30 = 1.36 GiB, scaled down for sequence length. The benchmark fed 33 synthetic frames (bench README line 7); with the VAE's 4 times time compression (1 + 32/4 = 9 latent steps) and 98 tokens per latent step (proxy PLAN line 121, verified) that is 9 x 98 = 882 video tokens, the count the benchmark's own FLOPs basis uses (bench README line 38, verified). A real training sample is 9 frames per view at offsets 0, 4, ..., 32 of a 33-step window (proxy PLAN line 57, verified), so 3 latent steps (`src/proxy_wam.py` line 63, `LATENT_T = 3`, verified) and 3 x 98 = 294 video tokens. So the benchmark's video sequence was 3 times longer than a real sample's; this follows from the cited lines. The scaling of memory with tokens is only roughly linear, and the 32 action and 128 text tokens do not scale, so the real reduction is a little under 3 times; on the other hand the benchmark's 5.1 GiB also held VAE-encode intermediates that the cached-latent step does not have. Which end of the range is more likely: the lower end (speculative).
5. **Peak memory and fit, `none` configuration:** about 25 to 34 GiB at micro-batch 1 (static part of prediction 3, autocast copies included, plus prediction 4). Does not fit a 24 GB card at any micro-batch under the fp32 recipe; fits a 48 GB card at a micro-batch somewhere between 4 and 32 (the autocast copies take away a few GiB of headroom); an 80 GB card allows a micro-batch at least twice as large. Source: predictions 3 and 4.
6. **Speed, `none` configuration, on an A6000-class card:** between about 0.05 and 0.14 s per sample for forward and backward, so about 6 to 18 s per optimizer step of 128 samples. Source: the LOG entry's arithmetic, (1.525 - 0.479) / 2 = 0.52 s per sample without the VAE, x 8/30 = about 0.14 s; the lower end applies the 3 times sequence correction of prediction 4. The benchmark ran with bf16-resident weights (bench README line 61, verified: "Resident bf16 weights"), not this plan's fp32 weights under bf16 autocast, so it did not pay autocast's repeated weight casts or fp32 optimizer traffic; the real figure may be off in either direction (slower from the casts and fp32 traffic, faster from the shorter sequence than the 8/30 scaling assumes). The AdamW update for about 1.7B parameters adds well under a second per optimizer step (speculative). Cards other than the A6000 differ by a factor not measured in this repo.
7. **One full training run** (21,696 optimizer steps of 128, the proxy's 10 epochs, proxy PLAN line 287, verified): about 36 to 108 card-hours on an A6000-class card. The LOG entry gave about 107 A6000-hours and "roughly $40 to $90 on Runpod and $150 or more on Modal per run" (direction `LOG.md` 2026-11-12, its own arithmetic, speculative there). Evaluation is not included in either figure.
8. **One extra encoder** (about 1,024 to 1,152 more input channels): adds a few percent at most to time and memory, since only the patch embedding, the head and the loss over the extra channels grow; the 294-token sequence and the 8 blocks are unchanged. Source: the proxy's input design (`src/proxy_wam.py` lines 15-16, 377).
9. **Loss at start:** finite in both configurations; the video part close to, or above, the predict-zero baseline, because the truncated stack no longer forms the computation its blocks were trained in. No decision rests on this prediction.

## Decision rule
Fixed before running. **This check produces a cost and a fit list, not a research finding.** It says nothing about whether the pretrained start, the 8-layer cut, or any encoder helps, and nothing from it goes into the README key findings.

**Load outcome (step 4):**
- Every kept block loads with zero difference, and the only `new` and `skipped` tensors are the expected ones (prediction 1): go on to the measurement.
- A shape mismatch, an unexplained missing or unused tensor, or a nonzero difference: stop, record it in `LOG.md`, and fix only code (loading or name mapping). One rerun is allowed inside the same paid session's cap. A second failure goes back to the lead and the user; no timing is reported from a model that did not load as intended.

**Fit list (from the sweep's peaks):**
- **M** is the total memory the card itself reports, in bytes (`torch.cuda.get_device_properties(0).total_memory`), not the nominal size in its name; cards sold as "48 GB" report less than 48 GiB, and by different amounts (for example A40 and L40S lower than RTX A6000; recalled, the PR #27 review's point, not checked here). The **peak** is `torch.cuda.max_memory_reserved` in bytes, the same figure the Step 6 m* rule reads.
- The model "fits" a card at micro-batch m if the peak at that m (the larger of the sweep peak and, at m*, the optimizer-step peak; both after the first optimizer update) is at most 0.9 x M (10% left for fragmentation and other processes). For each configuration the report lists the largest m that fits on the measured card. For the 24 GB, 48 GB and 80 GB classes not measured, it uses the linear fit of peak against m and each card's reported total memory, read on the day from the provider's or NVIDIA's listing (or nominal size, said so, if no figure is found), labelled as an extrapolation.
- Fits 48 GB at m* of 1 or more: full runs can use the 48 GB class (A40, RTX A6000, L40, L40S), the class Nautilus has (bench README line 12, verified).
- Fits only 80 GB: full runs need A100 80 GB-class cards, or a memory change (Open item 4; gradient checkpointing was refused by Fast-WAM's compiled path in the 2026-10-16 benchmark, bench README line 63, verified). Which one is the user's call.
- Does not fit 80 GB at m = 1: stop; back to the lead and the user with the measured peak.

**Cost of one full training run (filled in from the measurement):**

card-hours = S x t_step / 3600, and dollars = card-hours x p

- S = optimizer steps in one full run = 21,696 (10 epochs at global batch 128 over the 1,712 training episodes; proxy PLAN line 287, verified). If the real-run plan changes epochs or batch, S changes with it.
- t_step = measured seconds per optimizer step at global batch 128, on the card type that would run the full run, at the m* that card allows (step 6, "Full optimizer steps"). A t_step measured on a different card type is not transferred by an assumed ratio; it is reported as "measured on X" and the full-run card is named.
- p = that card's hourly price on the day it is read (step 1); p = 0 for Nautilus, whose cost is queue time and the utilisation rules instead (`STANDARDS.md`, compute budget).
- Excluded and stated next to the figure: evaluation (LIBERO and LIBERO-Plus rollouts), data loading stalls, checkpoint writes, startup, failed runs, and, for a paid provider, storage and transfer of the full feature caches the run reads (the 2.5 GB slice of this check hides this): the VAE latents, about 31.4 GB by arithmetic, plus the chosen encoder's cache, DINOv3 223 GB, C-RADIOv4 251 GB or SigLIP 2 251 GB (`data/README.md` line 67, verified; about 756 GB for VAE plus three encoders, proxy PLAN line 125, verified). These come on top, and the storage and transfer part is priced on the day if a paid full run is ever proposed.

**What the cost leads to:**
- If dollars for one full run on the cheapest suitable paid card exceed the user's paid budget of about $30 a month, full runs do not go on the user's own money: they go to Nautilus (free; user decision (e) of 2026-11-12 as the direction `LOG.md` records it: paid compute "for short jobs only, long training stays on Nautilus") or to compute from the PI ask, and the figure goes into that ask. If it is under the budget, whether to pay for a run is still the user's decision, asked per run.
- The card-hours figure, with the `none` and one-encoder numbers side by side, is the measured cost per run the user wanted before the PI meeting (direction `LOG.md` 2026-11-12, Next).

## Cost and time cap
The user's condition is that this check is fast and cheap.

Two limits, because the script is not the only thing that bills.
- **Inner limit, the script: 60 minutes,** enforced in the command: `timeout --signal=TERM --kill-after=60 3600 <launcher that runs the per-process steps of Step 6 in order>` (GNU coreutils, recalled; the launcher and its arguments are the implementation session's). A run that hits it keeps what it has (each sweep row is written as its process ends).
- **Outer limit, total billed time: 90 minutes** from the moment the machine starts billing until it is stopped. Pod or container start, image pull, environment install, weight download and data copy-in all bill but happen outside the script's `timeout`, so they are inside this limit and not the inner one. Where the provider has a hard lifetime limit, it is set to 90 minutes: on Modal the function's `timeout` argument (recalled; whether Modal bills image builds separately is read on the day). On Runpod the pod's command ends with `; runpodctl stop pod "$RUNPOD_POD_ID"` (`;`, not `&&`, so the pod stops even when the script fails or is killed by the inner limit; `runpodctl` usage recalled; a Runpod pod keeps billing after its process exits unless stopped, recalled); whether Runpod offers a lifetime limit on a pod is read in its docs on the day, and if it does not, the implementation session stops the pod itself at 90 minutes at the latest and checks with `list-pods` that it is stopped. On Vast.ai the equivalent is read from its docs on the day. If it runs on Nautilus instead, the 90-minute limit on running time is enforced inside the pod: an outer `timeout` of 5,400 s around the whole container command (environment install, weight download and the launcher), with the inner 3,600 s `timeout` around the measurement launcher. The Job's `activeDeadlineSeconds` is not the 90-minute limit, because it counts from Job creation, so queue time uses it up (recalled), and queues of hours are common (Open item 2); it is set long enough to cover queueing as well, following `_standards/08-compute-nautilus.md` and the implementation session's practice, and its value is chosen there, not here.

On Modal the same question is answered with Modal's own volume or image mechanism.

## Open, for the user
Design choices this plan does not make. Each has options and a recommendation; none is decided.

1. **Which 8 of the 30 layers to keep.**
   - First 8 (blocks 0-7). Each kept block still receives the kind of input it was trained on from the blocks before it, up to block 7; the top of the stack is gone. Simplest reading of the mentor's "pre-trained weights on 8 layers".
   - Evenly spaced (for example blocks 0, 4, 8, 12, 17, 21, 25, 29). Keeps blocks from the whole depth, but every block after the first sees inputs from a different block than in training.
   - Other (last 8; first 4 plus last 4; first 8 then grow toward 30 in later runs, as the mentor suggested increasing depth).
   - Memory and speed should not depend on the choice: all 30 blocks have the same shapes, so any 8 cost the same. **This is the worker's reasoning, not verified** (no block-level measurement exists in this repo, and Fast-WAM's config is not read here). If that holds, the sizing check can run before the choice is settled, with blocks 0-7 as a placeholder tagged "placeholder, not the user's choice" in every results file (Step 4). The placeholder is not a choice for any real run and carries over to none; the loss-at-start figure is the only output that depends on the set, and it carries no decision.
   - Recommendation (the worker's, for the user to accept or reject): first 8 for the first real run, because each kept block's input stays closest to what it saw in training (speculative), and growing depth from there follows the mentor's suggestion. The choice stays the user's.

3. **Which extra encoder for the one-encoder case.**
   - DINOv3 (1,024 channels): the paper's base encoder, and the first single-encoder real run will likely use it.
   - C-RADIOv4 or SigLIP 2 (1,152 channels each): the widest single encoder we have cached, so an upper bound for one-encoder cost.

4. **Precision recipe** (sets most of the memory). Options: the proxy's fp32 weights with bf16 autocast and fp32 AdamW (what the code does now); bf16 weights and gradients with fp32 optimizer states; an 8-bit optimizer. Recommendation: measure the proxy's recipe, since it is the one the current code and its tests use, and treat the others as fixes only if the fit list forces one.

For the widened input: copy the pretrained 48-channel slice and set the extra-channel slice to zero, so the model starts as the pretrained one; or initialise the extra slice randomly. For the action expert: as Fast-WAM does (step 2), or from a published LIBERO checkpoint if one exists.
