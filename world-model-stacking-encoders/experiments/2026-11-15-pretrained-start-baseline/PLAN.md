## In plain words
This is stage 1 of decision 006: train the model that starts from the pretrained Wan 2.2 video transformer, cut to its first 8 layers, with no extra encoder, on the paper's clean LIBERO training data, then test it in the simulator on clean LIBERO. The question is simple: does this model actually do the robot tasks? The from-scratch 8-layer proxy almost never did, so before any encoder pairing is compared on this model, it has to be shown to work. The bar it has to clear is written below as options; the user picks one before training starts, and what happens after each outcome is written now, so no result can move the goalposts.

## Question
Does the 8-layer pretrained-start world action model (Fast-WAM's `FastWAMJoint`, video expert loaded from Wan 2.2 TI2V-5B blocks 0-7, no extra encoder), trained on the paper's 1,712 clean LIBERO episodes with the paper's training settings as far as compute allows, reach the pass bar on clean LIBERO (four-suite average success over 2,000 simulator rollouts, the paper's protocol)?

**Why this comes before any encoder.** (1) Decision 006 (c) item 1 makes it the first stage of "done" (`decisions/006-research-question-and-done.md` line 14, verified). (2) Stage 2 asks why some encoder pairings help and others hurt (decision 006 (a), line 11, verified). A pairing can only be judged against a base model that completes tasks; on a model that almost never succeeds, a few-point change is unreadable. That is what happened to the from-scratch proxy: its two full-length DINOv3 models averaged 8.315 and 7.155 points on LIBERO-Plus against the paper's 84.0 (`experiments/2026-10-27-proxy-calibration/PLAN.md` line 272, verified), and its 500-step pilot checkpoints had 0 of 40 clean LIBERO successes each (same PLAN line 166, verified). (3) The mentor asked to "Start with clean training and clean testing" and to start "with pre-trained weights (on 8 layers, as tested. Then increase depth" (direction `LOG.md` 2026-11-15 [agent, lead, planning], the mentor's notes verbatim, lines 1841 and 1844, verified). (4) If the bare model fails, adding an encoder cannot tell us whether the encoder or the base is at fault, so a failure here is cheaper to find now than inside stage 2 (speculative reasoning).

Departures, each with its reason:
1. **Depth: 8 of 30 layers in both experts.** Reason: the user's decision (decision 005 (c), line 13, verified: "at 8 layers first as the mentor suggests, and increase depth later") and the mentor's note (above). Cost is also the reason the mentor gave the order; a 30-layer run is not sized. Effect (speculative): the main expected gap to the paper.
2. **Micro-batch 8 with 16 accumulated micro-batches per optimizer step.** Reason: global batch 128 does not fit on one 48 GB card; m* = 8 on the L40S (sizing LOG line 35, verified). On a card that cannot hold micro-batch 8, m = 4 with 32 accumulated micro-batches (the global batch stays 128; the rule is under "Parameters set from measurements").
   **Random draws are made once per optimizer step, not per micro-batch (a requirement).** `training_loss` draws the video noise, the video timesteps, the action noise and the action timesteps inside each call, sized to that call's batch (`src/proxy_wam.py` lines 401-408, verified), and `pretrained_sizing.micro_step` calls it once per micro-batch (lines 499-506, verified). Sixteen calls of 8 therefore draw different numbers, in a different order, from one call of 128, so naive accumulation matches a batch of 128 only in distribution, and only if Fast-WAM's `sample_training_t` draws each sample's timestep independently, which is not checked here (Fast-WAM's source is not in this repo). The design instead: at each optimizer step the training script draws the noise and timesteps for all 128 samples at once, from a generator seeded by (training seed, optimizer step), with the same calls and shapes `training_loss` makes for a batch of 128, and passes each micro-batch its slice. Each micro-batch's loss is scaled by its share of the batch (8/128) before backward. What is then identical to one batch of 128: the samples, the noise and timesteps of every sample, each sample's loss (each is normalised on its own, then averaged, lines 416-426), the loss weights, and the averaging over 128. What is not identical: floating-point summation order in the accumulated gradient, and bf16 autocast kernels that may differ with batch size, so gradients agree to a tolerance, not bit for bit (speculative size: small). Because the draws are keyed by the step, they also do not depend on the micro-batch size or on RNG state carried across a resume. Any other randomness in the forward pass (dropout) is expected to be absent in Wan's blocks (recalled, not checked); the implementation session confirms it. Gradient checkpointing is not available in Fast-WAM's MoT, so it is not a lever (`step2-reading.md` line 66, verified).
3. **Precision (proposed, pending Open item 8): fp32 weights with bf16 autocast and fp32 AdamW** instead of the paper's "bfloat16" (Table 6 does not say whether weights, or only computation, are bf16). Reason: this is the recipe the sizing run measured and the proxy's tests use (sizing PLAN line 18, verified); Fast-WAM's own configs build the model in bf16 (`step2-reading.md` line 17, verified), so a pure-bf16 recipe would be closer to Fast-WAM but is unmeasured for memory and speed. Effect (speculative): at least as precise as the paper's; slower than pure bf16. Open item 8.
4. **Action expert at 8 layers, not 30, and its initialisation** (Open item 2). Fast-WAM resizes the Wan video weights into the action expert by linear interpolation with alpha scaling, keeping only the 7-dim in and out projections fresh (`step2-reading.md` lines 50-53, verified); the paper does not say what it did. The sizing run used fresh weights (sizing LOG line 62).
5. **16-episode buffers instead of a full shuffle.** Reason: disk reads on CephFS (proxy PLAN line 135, verified: "a deviation from a full shuffle, logged in PLAN"). Same as the proxy and the sizing run.
6. **No validation split (proposed, pending Open item 7).** The paper's Table 7 note says dataset sizes are "counted before the validation split" (p18) but gives no size; the proxy trained on all 1,712 episodes. The worker's argument for training on all of them: this run selects no checkpoint and tunes nothing, so a validation set would have no job here (speculative reasoning). The user decides.
7. **Cached VAE latents and T5 embeddings instead of running the frozen VAE and T5 inside the step.** Both are frozen, so caching is the same computation done once (proxy PLAN lines 99 and 125, verified) **only if Fast-WAM's LIBERO training applies no random image augmentation** before the VAE. No file in this repo says whether it does. If it does, the cache freezes one unaugmented view of every clip and this is a real departure (the model never sees the augmentation), conditional on the reading task in the Hand-off; its consequence is Open item 10. Separately, the latents were computed in bf16 and stored float16, a rounding the live path would not have (speculative effect: negligible).
8. **One card, one training seed** (Open item 5). The paper reports one trained checkpoint per configuration (paper App. C.2, p17, verified) and does not state its compute (paper note line 17, verified).

Anything in Table 6 or 7 not listed above is matched.

### Checkpointing and resume
A run is about a day of card time (23.54 L40S-hours measured basis, sizing LOG line 41) and Nautilus pods can be lost, so:
- **What is saved:** model state, AdamW state, the optimizer step (counted in full optimizer steps of 128), CPU and CUDA RNG states, as `save_ckpt` does (`proxy_wam.py` lines 515-519), plus the micro-batch size used. Checkpoints are written only between optimizer steps, never in the middle of an accumulation.
- **How often:** every K optimizer steps, K a declared parameter (rule under "Parameters set from measurements"): the multiple of 100 optimizer steps closest to 45 minutes of measured step time. At the L40S's measured 3.907 s per step that is 2,700 s / 3.907 s = 691 steps, so K = 700, about 45.6 minutes per checkpoint (arithmetic); on another card K follows that card's measured step time. The proxy's default of 1,000 steps (`--ckpt-every`, line 539) would be about 65 minutes at that step time.
- **Where:** `--out`, and so `ckpt.pt`, lives on the shared PVC `stacking-encoders-proxy` (under `/mnt/proxy/runs/`, the proxy's convention, `STANDARDS.md` line 61, verified), never on pod-local disk, because a local copy dies with the pod. If writes to CephFS stall, a checkpoint may be staged on local disk first, but it counts as written only once the renamed file is on the PVC. On a paid provider the equivalent is a volume that outlives the machine (Open item 3).
- **Size:** about 20 GB per checkpoint (1.68 B parameters x 12 bytes for fp32 weights and the two AdamW moments; arithmetic, speculative until written). Written to a `.tmp` file and renamed, as `save_ckpt` does, so a lost pod leaves the previous checkpoint intact. The PVC had 235G free at about 08:15 UTC on 2026-11-15, before the Wan shard 2 download finished (direction `LOG.md` line 1818, verified); the implementation session checks free space before the run. Where checkpoints go on a paid provider is part of Open item 3.
- **Resume:** a restarted run finds `ckpt.pt` in its `--out` folder and continues from its step with the same plan and schedule (as `proxy_wam.py` lines 561-566). The data plan depends only on the seed and the episode list (`make_plan`, line 270), and the noise and timestep draws only on the seed and the optimizer step (departure 2), so a resumed run sees the same batches and the same draws whatever card it lands on.
  - Same micro-batch as before the interruption: the resumed run must reproduce a straight run bit for bit (as proxy check "checkpoint resume reproduces a straight run bit for bit", proxy PLAN line 137); tested on CPU.
  - Different micro-batch (a restarted pod lands on a card that cannot hold the recorded one; the micro-batch rule under "Parameters set from measurements" is applied again on the new card): the resumed run computes the same per-sample losses and the same averaged gradient up to floating-point order, but not bit for bit. The change is written to the checkpoint metadata and logged in this folder's `LOG.md` with the step at which it happened.
- **At the end:** `model.pt` (model weights in fp32, about 6.7 GB by arithmetic, and the config in the format `rollout.py` reads, see Evaluation) and `train.json` (loss history), as `proxy_wam.py` lines 574-576. **The new script does not delete the last checkpoint:** the reused proxy code deletes `ckpt.pt` at the end (`proxy_wam.py` lines 577-578, verified), and that step is removed. The last `ckpt.pt` is kept until the evaluation has loaded `model.pt` once; deleting it after that needs the user's OK (deleting data is gated, proxy PLAN "Gates", line 245, verified).

### Sanity checks before the full run (`../../../_standards/07`, "Sanity checks before scaling", lines 19-24)
1. **Overfit one batch:** the built and loaded model, one fixed batch of 8 windows, a few hundred optimizer steps at a constant learning rate; the training loss falls well below its starting value and below the predict-zero baseline on that batch. Pass mark set by the implementation session before running it, from the proxy's check 9 (proxy PLAN line 137).
2. **Loss at start:** already measured in the sizing run on one batch of 16 for `none`: model total 3.735 (VAE 2.634, action 1.101) against predict-zero 2.526 (VAE 1.492) (sizing LOG line 38, verified). Repeated on the full data's first batch and logged; a non-finite loss stops.
3. **Inputs inspected:** done for the same caches in the sizing run (`experiments/2026-11-12-pretrained-start-sizing/results/run1/sanity-<config>.json`, sizing PLAN Step 5); repeated on the first batch of the full data (shapes, ranges, padding counts, task strings).
4. **End to end at small scale, evaluation included:** a short training run (the same script and settings, a few hundred optimizer steps, its own `--out`) followed by a timed smoke evaluation of 40 rollouts, one per clean task. This checks that `rollout.py` loads and runs the new model and measures rollout time (see "Evaluation time"). **The smoke must not produce test outcomes. Requirements:**
   1. Before the smoke, the implementation session reads how many init states each clean task's `.pruned_init` file holds (reading only; recalled as 50 for LIBERO, not checked here) and logs the counts.
   2. If every task has more than 50 states, the smoke runs one trial per task on state index 50 (a small `rollout.py` option to start clean trials at a given index, by PR). Those states are never part of the final evaluation, so the smoke's success values may be read.
   3. Otherwise (the likely case), the smoke runs in a timing-only mode, a `rollout.py` flag by PR. Leaving out the success field is not enough: `run_episode` ends an episode as soon as the task is done (`src/rollout.py` lines 396-398, verified), so a successful episode has fewer steps and less wall time than a failed one, its record also carries `final_state` (lines 405 and 470-471, verified), and the smoke subcommand's log prints success per episode (line 718, verified). **Requirement:** in timing-only mode the done signal is ignored and every episode runs to its step limit (400 or 700 steps after the 30 wait steps), and the records and logs carry no success, no step count at success, no final state and nothing else computed from the done signal; they hold only the job key, wall time, the fixed number of steps run, errors, and the pod's GPU, CPU and memory use. A test with a fake environment that reports success early checks that the records and log lines are identical to those of a fake environment that never succeeds.
   4. Either way the smoke writes to its own records file, never the final evaluation's: `rollout.py` resumes from its `--out` file and skips every record already there (docstring lines 36-37; `done_keys`, lines 474-481), so a shared file would make the final run skip jobs.
   The worker considered the reviewer's alternative, a randomised reset (skipping `set_init_state` under a different environment seed), and did not choose it: how LIBERO behaves without `set_init_state` is recalled, not checked, and if its random reset draws from the same distribution the fixed states came from (recalled, not checked), it does not guarantee states different from the 50 test states. The timing-only mode is checkable by a test. The smoke is logged as a test-task use in either branch (`../../../_standards/07` line 6). The same timing-only mode is used for the LIBERO-Plus timing shard (see the pass-bar section, option 4).

### Evaluation on clean LIBERO (the paper's protocol)
- **Protocol:** 50 rollouts per task across 40 tasks, 2,000 rollouts per evaluation; reported as "the average across its four equally sized suites" (paper App. C.2, p17, verified; Sec. 4.1, p5: "following Fast-WAM"). In `rollout.py`: `--clean 50` (init states 0 to 49 of each base task) under eval seed 41 (`--clean-seed 41`). The paper does not state an eval seed for clean LIBERO; 41 is the first of its LIBERO-Plus seeds (App. E.3, p22) and `rollout.py`'s default.
- **Inference settings:** 10 inference steps, replanning every 10 steps, 30 initial waiting steps, no action ensembling, text guidance scale 1.0, binarized gripper (paper App. E.3, p22, verified, stated there for the composition evaluations; Sec. 4.1 says clean LIBERO follows Fast-WAM); max steps 400 / 700 from Fast-WAM (proxy PLAN line 59, verified). All are `rollout.py`'s current constants.
- **Which checkpoint:** only the final one (step 21,696). No intermediate checkpoint is evaluated on the test tasks, so nothing is selected on them (`../../../_standards/07` line 6).
- **Reported:** four-suite average success (the pass-bar number), per-suite success, per-task success, mean episode length, and the binomial standard error of the average (about 1.1 points at 50% success over 2,000 rollouts; arithmetic, sqrt(0.25 / 2000)). One training seed, so this error describes rollout sampling only, not training-seed spread.
- **Which card it runs on: Open item 11.** The user chose L4-only for evaluation after NRP's idle-GPU warning on faster cards (proxy PLAN Amendment 2026-11-07, line 260, verified), with the account assumed at 1 of 3 strikes (`STANDARDS.md` line 48), and the named A40 and RTX A6000 resources are "added only with the user's OK" (proxy PLAN line 257, verified). So evaluation starts on Nautilus L4, and moving it off L4 is a stop for the user, never the implementation session's call. Whether an L4 holds the new model and keeps the GPU above 40% is what the smoke measures (speculative: about 6.7 GB of fp32 weights should fit in 24 GB, and a larger model may raise GPU use).
- **What exists and what must change** (the implementation session's work, by PR):
  - `rollout.py` builds the policy with `PW.build_model(cfg["in_dim"], device, **cfg["model_kw"])` (lines 290-294). If the new training script writes `model.pt` with `model_kw` = the Wan widths (`hidden` 3072, `action_hidden` 1024, `heads` 24, `head_dim` 128) and `layers` 8, the existing loader may build the right model unchanged (`build_model` takes exactly these arguments, `proxy_wam.py` line 372, and gives FFN 14336 at width 3072, `step2-reading.md` line 46). This is speculative until a test loads a saved new-model `model.pt` through `Policy.load` and compares parameters.
  - `--cuda-graph` replays the denoising loop from one CUDA graph (docstring lines 31-33); whether capture works and fits memory at this size is unmeasured.
  - The `Featurizer` for config `none` runs only the Wan 2.2 VAE on the current frame (docstring lines 13-16); unchanged.
  - Nothing in `lp_eval.py` is needed for the pass bar; the clean records are tallied by a short script or an `lp_eval.py` addition, written with a synthetic test.

### Evaluation time (not measured yet)
The proxy's speeds (484 and 449 episodes per pod-hour, proxy PLAN line 166) were for a 31.6 M-parameter model whose episodes mostly ran to the step limit. The new model has about 53 times more parameters (arithmetic: 1.68 B / 31.6 M), so each policy call costs more, while successful episodes end early (speculative, direction unknown). At the proxy's speed, 2,000 rollouts would be about 4.1 to 4.5 pod-hours (arithmetic), which is a floor-of-guesses, not an estimate. **How it gets measured:** the 40-rollout smoke evaluation in sanity check 4 records each rollout's wall time (`rollout.py` line 405), the pod's GPU use over 10-minute windows, its CPU and memory. In the timing-only mode every episode runs to its step limit, as a failed episode does, so the smoke gives an upper bound on the time per episode, not the expected time; the real evaluation, where successful episodes end early, then takes at most that per-episode time times the number of episodes (up to differences in policy batching across environments, which the deadline's margin covers; speculative). This is the safe direction for setting deadlines. From it the implementation session sets the shard count, the environments per pod and the deadline for the 2,000-rollout evaluation, and logs the estimate before submitting it. ### Parameters set from measurements (declared now; setting them is not a design change)
Each is set by the implementation session from a measurement after the lock, by the rule given, and logged with the measurement in this folder's `LOG.md`.
- **Micro-batch per card:** the largest of 8 and 4 whose peak `max_memory_reserved` over the first optimizer steps on that card is at most 0.9 x the card's reported total memory (the sizing check's fit rule, sizing PLAN line 84, verified). Global batch stays 128. If 4 does not fit, stop and ask the user. Applied again after a resume on a different card.
- **Checkpoint interval K:** the multiple of 100 optimizer steps closest to 45 minutes of the measured step time, kept between 30 and 60 minutes.
- **Training time limit:** set by the user's choice on Open item 4 from the first-minutes projection.
- **Evaluation shard count and environments per pod:** from the smoke, on L4. Environments per GPU are raised until the smoke shows the GPU at or above 40% over 10-minute windows. If the model does not fit on an L4, or the GPU stays below 40% after raising environments, stop for the user (proxy RUN.md stop 10, line 33): the card is the user's choice (Open item 11), not a parameter. ### Test-set use
Clean LIBERO rollouts are the test. They are used twice: the 40-rollout smoke (off the final test states, or timing-only with no success field written; see sanity check 4) and the final 2,000-rollout evaluation of one checkpoint. Both are logged in this folder's `LOG.md` with date and checkpoint. No hyperparameter, checkpoint or recipe choice is made from either. A re-evaluation of the same checkpoint is allowed at most once, only after a pipeline fault has been shown without using test outcomes (see the fail branch); both evaluations are then reported side by side and the amendment says the first result had been seen.

- The paper's LIBERO-Plus protocol, which the user also chose for every proxy checkpoint: all 10,030 episodes under each of evaluation seeds 41, 42 and 43 (paper App. E.3, p22; user's decision of 2026-11-05, proxy PLAN "Amendment 2026-11-06", lines 172 and 175, verified). For the proxy model this cost about 64 to 70 GPU-hours per checkpoint (proxy PLAN line 290, verified).

**Options for the bar** (B is the four-suite clean average, in percentage points):
1. **Near the paper: B >= 90.** Reasoning: within about 8 points of the paper's 97.9, so stage 2 would run at nearly the paper's scale. Trade-off: it tests depth more than usefulness; the paper reports no clean numbers for pairs at all (Table 10 is LIBERO-Plus only, LOG line 1864), and its single-encoder clean numbers all sit near 98 (LOG line 1865), so clean success says little about stage 2's question, and a model at 75 may serve stage 2's LIBERO-Plus question as well as one at 92, and missing this bar sends the work to deeper, costlier models.
2. **A working policy: B >= 50, and every suite >= 25.** Reasoning: the model completes about half the tasks, with no suite near zero, leaving room both up and down for stage 2's effects. Trade-off: the numbers are round, not derived from a source; the per-suite floor guards against a model that solves only the short suites.
3. **Derived from the user's earlier level target: B >= 36.** Reasoning: the paper's VAE-only model keeps 74.7 / 97.9 = 0.763 of its clean success on LIBERO-Plus (arithmetic); a LIBERO-Plus score of 27 (the user's 2026-11-09 target) would then need about 27 / 0.763 = 35.4 on clean, rounded up to 36. Trade-off: the ratio comes from a strong model; a weaker model probably loses more under perturbation (speculative), so 36 is likely a lower bound for reaching 27 on LIBERO-Plus, not a guarantee. **Used alone, option 3 contains no LIBERO-Plus check:** a model can pass at 36 and still sit below 27 on LIBERO-Plus, which would only show up in stage 2. The 27 itself may not carry over from the proxy (source list above).
4. **Two zones: B >= 90 pass; 36 <= B < 90 conditional pass; B < 36 fail.** Reasoning: combines options 1 and 3; a clear pass needs no further check, a middle result proceeds only if the model reaches 27 on LIBERO-Plus (below), a low one stops. **The LIBERO-Plus protocol for that check is fixed now:** the paper's full protocol, all 10,030 episodes under each of evaluation seeds 41, 42 and 43, the total being the mean of the three full-benchmark success rates (paper App. E.3, p22), the same protocol the user chose for every proxy checkpoint (proxy PLAN lines 172 and 175), with `rollout.py`'s LIBERO-Plus settings as used for the proxy. Its cost on the new model is not measured; for the proxy model it was about 64 to 70 GPU-hours per checkpoint (proxy PLAN line 290), and the new model is likely to cost more per rollout (speculative). It is measured before submission from a timing-only LIBERO-Plus shard (one episode per suite-category cell, the layout of `rollout.py`'s `smoke_jobs`, lines 598-608, run in the timing-only mode of sanity check 4, so no LIBERO-Plus outcome is seen), and the estimate is logged before the evaluation is submitted. Trade-off: more rule to apply, and under Prediction 4 (50 to 80) the middle zone is the likely outcome, so in practice the gate is likely the LIBERO-Plus total of 27, at the cost of a full LIBERO-Plus evaluation that stage 2 would need anyway (Open item 6). The 27 caveat above applies.

**The worker's recommendation (for the user to accept or reject, not a decision):** option 4, unchanged after the review. It ties the lower line to a target the user already chose for the same purpose (an effect of the paper's size must be readable), keeps the paper's level as the clear-pass line, and now checks that purpose directly on LIBERO-Plus with the protocol fixed in advance. Its cost is a full LIBERO-Plus evaluation of this checkpoint, which stage 2 needs as its no-encoder reference in any case. If the user prefers one line and no LIBERO-Plus evaluation in stage 1, option 3, with the limit stated above.

**What happens for each outcome** (written before any result; the same for any option, with "pass" and "fail" read against the chosen bar, and "conditional pass" existing only under option 4):
- **Pass.** Stage 2 starts (decision 006 (c) item 2, line 15): DINOv3 alone, one helpful pairing and the harmful pairing, fused by channel-wise concatenation, on clean LIBERO first and then LIBERO-Plus, all with this recipe and this checkpoint's `none` run as the no-encoder reference. Stage 2 gets its own PLAN, with its seed count (Open item 5).
- **Conditional pass (option 4 only, 36 <= B < 90).** This checkpoint is scored on LIBERO-Plus with the protocol fixed under option 4 (full benchmark, seeds 41, 42, 43), after the timing-only shard has sized it and the estimate is logged. If its LIBERO-Plus total is at least 27 points, stage 2 starts as for a pass, and every stage 2 report states the clean-level gap to the paper's 97.9. If it is below 27, the "fail" options below apply.
- **Fail.** No encoder runs. First, a diagnosis that costs no new training, to separate a pipeline fault (for example observation preprocessing or the gripper sign in `rollout.py`) from a model that is simply too weak. The per-suite and per-task results are reported as they are, but **a pipeline fault must be shown without using test outcomes**: by code reading against Fast-WAM's eval code, an open-loop check of predicted against recorded actions on training windows, the training loss against the predict-zero baseline, a unit test that reproduces the fault, or rollouts on init states outside the 50 test states if the files hold any (sanity check 4). A fault shown that way is fixed by PR, and the same checkpoint is re-evaluated **at most once**; both evaluations are reported side by side, an amendment records it and says the first result had been seen, and the pass bar does not change. If the model is too weak, the next options go to the user, each with its cost from the sizing basis:
  1. **More layers** (for example 16, then toward 30, as the mentor suggested increasing depth). At 16 layers the static memory roughly doubles from the sizing run's fitted 28.90 GiB for `none` (sizing LOG line 46), so it would not fit a 48 GB card under the fp32 recipe (speculative arithmetic); it needs an 80 GB card or a lighter precision recipe (Open item 8), and a new sizing measurement.
  2. **Longer training** (for example 20 epochs): about twice the 23.54 L40S-hours, same cards (arithmetic). The paper trains 10 epochs, so this is a departure from the paper.
  3. **A pretrained action expert:** Fast-WAM's resized-from-Wan recipe if the run used a fresh one (Open item 2); or start from Fast-WAM's released LIBERO checkpoint, which is 30 layers, a different model class (base and optional-IDM, action attends to the first frame only) and has no stated weights licence (`step2-reading.md` lines 70-77, 106), so it is a model-class decision, not a drop-in.
  4. **A different set of 8 blocks** (for example evenly spaced), the sizing PLAN's Open item 1 options (sizing PLAN lines 117-122).
  Any of these is a new run with its own PLAN or amendment and its own bar; none is started without the user's choice.
