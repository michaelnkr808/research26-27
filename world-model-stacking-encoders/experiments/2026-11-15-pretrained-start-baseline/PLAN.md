## In plain words
This is stage 1 of decision 006: train the model that starts from the pretrained Wan 2.2 video transformer, cut to its first 8 layers, with no extra encoder, on the paper's clean LIBERO training data, then test it in the simulator on clean LIBERO. The question is simple: does this model actually do the robot tasks? The from-scratch 8-layer proxy almost never did, so before any encoder pairing is compared on this model, it has to be shown to work. The bar it has to clear is written below as options; the user picks one before training starts, and what happens after each outcome is written now, so no result can move the goalposts.

## Question
Does the 8-layer pretrained-start world action model (Fast-WAM's `FastWAMJoint`, video expert loaded from Wan 2.2 TI2V-5B blocks 0-7, no extra encoder), trained on the paper's 1,712 clean LIBERO episodes with the paper's training settings as far as compute allows, reach the pass bar on clean LIBERO (four-suite average success over 2,000 simulator rollouts, the paper's protocol)?

**Why this comes before any encoder.** (1) Decision 006 (c) item 1 makes it the first stage of "done" (`decisions/006-research-question-and-done.md` line 14, verified). (2) Stage 2 asks why some encoder pairings help and others hurt (decision 006 (a), line 11, verified). A pairing can only be judged against a base model that completes tasks; on a model that almost never succeeds, a few-point change is unreadable. That is what happened to the from-scratch proxy: its two full-length DINOv3 models averaged 8.315 and 7.155 points on LIBERO-Plus against the paper's 84.0 (`experiments/2026-10-27-proxy-calibration/PLAN.md` line 272, verified), and its 500-step pilot checkpoints had 0 of 40 clean LIBERO successes each (same PLAN line 166, verified). (3) The mentor asked to "Start with clean training and clean testing" and to start "with pre-trained weights (on 8 layers, as tested. Then increase depth" (direction `LOG.md` 2026-11-15 [agent, lead, planning], the mentor's notes verbatim, lines 1841 and 1844, verified). (4) If the bare model fails, adding an encoder cannot tell us whether the encoder or the base is at fault, so a failure here is cheaper to find now than inside stage 2 (speculative reasoning).

## Design

### Model
- `FastWAMJoint` as `src/pretrained_sizing.py` builds it: video expert at Wan 2.2 TI2V-5B width with blocks 0-7 loaded from `Wan-AI/Wan2.2-TI2V-5B` (revision above), input and output at 48 VAE channels (no widening, since there is no extra encoder), action expert 1024 wide at 8 layers (Fast-WAM's MoT requires equal depth in both experts, `step2-reading.md` line 44, verified), proprio encoder `Linear(8, 4096)`.
- Joint video-action denoising with the first-frame-causal video mask and action attending to all video (proxy PLAN line 129, verified). This is the paper's default formulation (paper App. B.1, p14, as the paper note records, `literature/notes/liu2026-what-visual-representations-wams.md` line 15, verified there).
- Action expert initialisation: Open item 2.
- No `torch.compile` (`compile_training_denoise` stays off; `step2-reading.md` lines 60 and 98, verified).

### Data
- All four suites of the cached 1,712 episodes (Open item 7 on a validation split), 33-step windows, 9 frames per view at offsets 0, 4, ..., 32, 3 latent steps, 294 video tokens, 32-step action chunks, umT5-XXL context of 128 tokens plus one proprio token, actions and proprio min/max-normalized as Fast-WAM (proxy PLAN lines 121-126, verified; `src/proxy_wam.py` lines 60-64).
- Data order from `make_plan` with the training seed and 16-episode buffers, as the proxy and the sizing run.

Departures, each with its reason:
1. **Depth: 8 of 30 layers in both experts.** Reason: the user's decision (decision 005 (c), line 13, verified: "at 8 layers first as the mentor suggests, and increase depth later") and the mentor's note (above). Cost is also the reason the mentor gave the order; a 30-layer run is not sized. Effect (speculative): the main expected gap to the paper.
2. **Micro-batch 8 with 16 accumulated micro-batches per optimizer step.** Reason: global batch 128 does not fit on one 48 GB card; m* = 8 on the L40S (sizing LOG line 35, verified). Accumulation gives the same gradient as one batch of 128 up to floating-point order (speculative, standard; the implementation session tests it, see Hand-off). On a card whose usable memory is lower than the L40S's, m = 4 with 32 accumulated micro-batches (the global batch stays 128). Gradient checkpointing is not available in Fast-WAM's MoT, so it is not a lever (`step2-reading.md` line 66, verified).
3. **Precision: fp32 weights with bf16 autocast and fp32 AdamW** instead of the paper's "bfloat16" (Table 6 does not say whether weights, or only computation, are bf16). Reason: this is the recipe the sizing run measured and the proxy's tests use (sizing PLAN line 18, verified); Fast-WAM's own configs build the model in bf16 (`step2-reading.md` line 17, verified), so a pure-bf16 recipe would be closer to Fast-WAM but is unmeasured for memory and speed. Effect (speculative): at least as precise as the paper's; slower than pure bf16. Open item 8.
4. **Action expert at 8 layers, not 30, and its initialisation** (Open item 2). Fast-WAM resizes the Wan video weights into the action expert by linear interpolation with alpha scaling, keeping only the 7-dim in and out projections fresh (`step2-reading.md` lines 50-53, verified); the paper does not say what it did. The sizing run used fresh weights (sizing LOG line 62).
5. **16-episode buffers instead of a full shuffle.** Reason: disk reads on CephFS (proxy PLAN line 135, verified: "a deviation from a full shuffle, logged in PLAN"). Same as the proxy and the sizing run.
6. **No validation split.** The paper's Table 7 note says dataset sizes are "counted before the validation split" (p18) but gives no size; the proxy trained on all 1,712 episodes. Reason for keeping all: this run selects no checkpoint and tunes nothing, so a validation set has no job here (speculative reasoning). Open item 7.
7. **Cached VAE latents and T5 embeddings instead of running the frozen VAE and T5 inside the step.** Reason: both are frozen, so the result is the same computation done once (proxy PLAN lines 99 and 125, verified); the latents were computed in bf16 and stored float16, a rounding the live path would not have (speculative effect: negligible).
8. **One card, one training seed** (Open item 5). The paper reports one trained checkpoint per configuration (paper App. C.2, p17, verified) and does not state its compute (paper note line 17, verified).

Anything in Table 6 or 7 not listed above is matched.

### Checkpointing and resume
A run is about a day of card time (23.54 L40S-hours measured basis, sizing LOG line 41) and Nautilus pods can be lost, so:
- **What is saved:** model state, AdamW state, the optimizer step (counted in full optimizer steps of 128), CPU and CUDA RNG states, as `save_ckpt` does (`proxy_wam.py` lines 515-519), plus the micro-batch size used. Checkpoints are written only between optimizer steps, never in the middle of an accumulation.
- **How often:** every K optimizer steps, with K set from the measured step time so that a checkpoint lands about every 30 to 60 minutes (at 3.9 s per step, K = 500 is about 33 minutes; arithmetic). The proxy's default of 1,000 steps (`--ckpt-every`, line 539) would be about 65 minutes at that step time.
- **Size:** about 20 GB per checkpoint (1.68 B parameters x 12 bytes for fp32 weights and the two AdamW moments; arithmetic, speculative until written). Written to a `.tmp` file and renamed, as `save_ckpt` does, so a lost pod leaves the previous checkpoint intact. The PVC had 235G free at about 08:15 UTC on 2026-11-15, before the Wan shard 2 download finished (direction `LOG.md` line 1818, verified); the implementation session checks free space before the run. Where checkpoints go on a paid provider is part of Open item 3.
- **Resume:** a restarted run finds `ckpt.pt` in its `--out` folder and continues from its step with the same plan, schedule and RNG (as `proxy_wam.py` lines 561-566). The data plan depends only on the seed and the episode list (`make_plan`, line 270), so a resumed run sees the same batches. Requirement for the code: a resumed run reproduces a straight run bit for bit, with accumulation, on a small CPU test (as proxy check "checkpoint resume reproduces a straight run bit for bit", proxy PLAN line 137).
- **At the end:** `model.pt` (model weights in fp32, about 6.7 GB by arithmetic, and the config in the format `rollout.py` reads, see Evaluation) and `train.json` (loss history), as `proxy_wam.py` lines 574-576. The last `ckpt.pt` is kept until the evaluation has loaded `model.pt` once, then deleting it needs the user's OK (deleting data is gated, proxy PLAN "Gates", line 245, verified).

### Evaluation on clean LIBERO (the paper's protocol)
- **Protocol:** 50 rollouts per task across 40 tasks, 2,000 rollouts per evaluation; reported as "the average across its four equally sized suites" (paper App. C.2, p17, verified; Sec. 4.1, p5: "following Fast-WAM"). In `rollout.py`: `--clean 50` (init states 0 to 49 of each base task) under eval seed 41 (`--clean-seed 41`). The paper does not state an eval seed for clean LIBERO; 41 is the first of its LIBERO-Plus seeds (App. E.3, p22) and `rollout.py`'s default.
- **Inference settings:** 10 inference steps, replanning every 10 steps, 30 initial waiting steps, no action ensembling, text guidance scale 1.0, binarized gripper (paper App. E.3, p22, verified, stated there for the composition evaluations; Sec. 4.1 says clean LIBERO follows Fast-WAM); max steps 400 / 700 from Fast-WAM (proxy PLAN line 59, verified). All are `rollout.py`'s current constants.
- **Which checkpoint:** only the final one (step 21,696). No intermediate checkpoint is evaluated on the test tasks, so nothing is selected on them (`../../../_standards/07` line 6).
- **Reported:** four-suite average success (the pass-bar number), per-suite success, per-task success, mean episode length, and the binomial standard error of the average (about 1.1 points at 50% success over 2,000 rollouts; arithmetic, sqrt(0.25 / 2000)). One training seed, so this error describes rollout sampling only, not training-seed spread.
- **Where it runs:** on Nautilus, L4 cards, as the proxy's later evaluation shards did after the idle-GPU warning on faster cards (proxy PLAN Amendment 2026-11-07, line 260, verified). Whether an L4 holds the new model and keeps the GPU above 40% is measured in the smoke step (speculative: about 6.7 GB of fp32 weights should fit in 24 GB, and a larger model may raise GPU use).
- **What exists and what must change** (the implementation session's work, by PR):
  - `rollout.py` builds the policy with `proxy_wam.build_model(cfg["in_dim"], **cfg["model_kw"])` (lines 290-294). If the new training script writes `model.pt` with `model_kw` = the Wan widths (`hidden` 3072, `action_hidden` 1024, `heads` 24, `head_dim` 128) and `layers` 8, the existing loader may build the right model unchanged (`build_model` takes exactly these arguments, `proxy_wam.py` line 372, and gives FFN 14336 at width 3072, `step2-reading.md` line 46). This is speculative until a test loads a saved new-model `model.pt` through `Policy.load` and compares parameters.
  - `--cuda-graph` replays the denoising loop from one CUDA graph (docstring lines 31-33); whether capture works and fits memory at this size is unmeasured.
  - The `Featurizer` for config `none` runs only the Wan 2.2 VAE on the current frame (docstring lines 13-16); unchanged.
  - Nothing in `lp_eval.py` is needed for the pass bar; the clean records are tallied by a short script or an `lp_eval.py` addition, written with a synthetic test.

## Predictions
Written before running. All speculative.
1. **Fit and speed.** Micro-batch 8 fits on an L40S, as measured; on cards that report less usable memory (A40 and L40S lower than RTX A6000 by the sizing PLAN's recalled note, line 83) micro-batch 8 may not fit and micro-batch 4 is used. Step time on A40, RTX A6000 and L40 is not measured; it could be either side of the L40S's 3.9 s (no assumed ratio, sizing PLAN line 94).
2. **Training time:** about 24 card-hours of steps on an L40S, plus checkpoint writes (about 45 writes of 20 GB at K = 500), startup and data waits; the proxy's data wait was about 12% of its loop at a 0.65 s step (proxy PLAN line 307, verified), and with a step about six times longer the loader should keep up more easily (speculative).
3. **Training loss:** falls below the predict-zero baseline within the first epoch and flattens in the second half, as the proxy's did (proxy PLAN line 296, verified for the proxy).
4. **Clean LIBERO, four-suite average:** clearly above the from-scratch proxy (0 of 40 at its 500-step pilot) and below the paper's VAE-only 97.9. A central guess of about 50 to 80 points, with wide uncertainty: the pretrained video blocks are the main reason to expect much better than the proxy, while the 8-layer cut, the action expert (fresh or resized) at 8 layers, and the absence of the 22 upper blocks are reasons to expect well below the paper. No measurement supports any number in this range.
5. **Per suite:** libero_10 (long-horizon, 700 steps) lowest; spatial and object highest.
6. **Evaluation time:** slower per policy call than the proxy, so more pod-hours per 1,000 rollouts unless many episodes end early on success.

## Pass bar and decision rule

**The pass bar is the user's decision. It is not chosen here.** The options below are fixed before any result exists. The bar applies to the four-suite average success on clean LIBERO, final checkpoint, 2,000 rollouts, protocol above. **Once the user signs off on a pass bar and this rule, both are locked** and change only by a dated amendment that states whether any result had been seen.

**Source numbers behind the options** (all verified in the files named):
- The paper's VAE-only reference (no extra encoder, channel-wise concatenation table): clean LIBERO average 97.9, LIBERO-Plus total 74.7 (paper Table 8, p19; direction `LOG.md` line 1863). Every single encoder with channel-wise concatenation lies between 98.0 and 99.1 on clean LIBERO (same LOG line). This model is taken to be 30 layers deep (inferred, LOG line 1862) and trained with the paper's full recipe.
- Fast-WAM's released optional-IDM LIBERO checkpoint: 97.75 percent average in first-frame mode and 98.55 percent in IDM mode, as published in its README, 30 layers, not reproduced here (`step2-reading.md` lines 72 and 75). No figure for Fast-WAM's base model was found in any file read here.
- The from-scratch 8-layer proxy: 0 of 40 clean rollouts for each 500-step pilot checkpoint (proxy PLAN line 166); its two full-length DINOv3 models averaged 8.315 and 7.155 points on LIBERO-Plus (proxy PLAN line 272). Their clean-LIBERO success was not read (proxy `LOG.md` line 928: "I did not read the clean-LIBERO success of the two DINOv3 models"); the records are in `experiments/2026-10-27-proxy-calibration/results/full-benchmark/rollouts/`, and a tally would be a cheap addition before sign-off (not done here: this worker runs nothing on result files).
- The user's earlier level target for the proxy: mean LIBERO-Plus success of at least 27 points, so that the 2.7-point harm threshold is at most a tenth of the model's own score (user's choice 2026-11-09, proxy PLAN lines 378 and 385, verified).

**Options for the bar** (B is the four-suite clean average, in percentage points):
1. **Near the paper: B >= 90.** Reasoning: within about 8 points of the paper's 97.9, so stage 2 would run at nearly the paper's scale. Trade-off: it tests depth more than usefulness; the paper's own clean numbers cannot separate helpful from harmful pairs (all near 98, LOG line 1865), so a model at 75 may serve stage 2's LIBERO-Plus question as well as one at 92, and missing this bar sends the work to deeper, costlier models.
2. **A working policy: B >= 50, and every suite >= 25.** Reasoning: the model completes about half the tasks, with no suite near zero, leaving room both up and down for stage 2's effects. Trade-off: the numbers are round, not derived from a source; the per-suite floor guards against a model that solves only the short suites.
3. **Derived from the user's earlier level target: B >= 36.** Reasoning: the paper's VAE-only model keeps 74.7 / 97.9 = 0.763 of its clean success on LIBERO-Plus (arithmetic); a LIBERO-Plus score of 27 (the user's 2026-11-09 target) would then need about 27 / 0.763 = 35.4 on clean, rounded up to 36. Trade-off: the ratio comes from a strong model; a weaker model probably loses more under perturbation (speculative), so 36 is likely a lower bound for reaching 27 on LIBERO-Plus, not a guarantee.
4. **Two zones: B >= 90 pass; 36 <= B < 90 conditional pass; B < 36 fail.** Reasoning: combines options 1 and 3; a clear pass needs no further check, a middle result proceeds with a stated condition (below), a low one stops. Trade-off: more rule to apply; the middle zone carries a stated condition rather than a judgement after the fact.

**The worker's recommendation (for the user to accept or reject, not a decision):** option 4. It ties the lower line to a target the user already chose for the same purpose (an effect of the paper's size must be readable) and keeps the paper's level as the clear-pass line, while a middle result still lets stage 2 start. If the user prefers one line, option 3, because it is the only option derived from a stated purpose rather than chosen round.

**What happens for each outcome** (written before any result; the same for any option, with "pass" and "fail" read against the chosen bar, and "conditional pass" existing only under option 4):
- **Pass.** Stage 2 starts (decision 006 (c) item 2, line 15): DINOv3 alone, one helpful pairing and the harmful pairing, fused by channel-wise concatenation, on clean LIBERO first and then LIBERO-Plus, all with this recipe and this checkpoint's `none` run as the no-encoder reference. Stage 2 gets its own PLAN, with its seed count (Open item 5).
- **Conditional pass (option 4 only, 36 <= B < 90).** Stage 2 starts as for a pass, with two conditions written into its PLAN: this baseline is scored on LIBERO-Plus first (Open item 6) and stage 2's encoder runs go ahead only if its LIBERO-Plus total is at least 27 points; and every stage 2 report states the clean-level gap to the paper's 97.9. If the LIBERO-Plus total is below 27, the "fail" options below apply.
- **Fail.** No encoder runs. First, a diagnosis that costs no new training: the training loss against the predict-zero baseline, the per-suite and per-task successes, rollout videos of a few failures, and an open-loop check of predicted against recorded actions on training windows, to separate a pipeline fault (for example observation preprocessing or the gripper sign in `rollout.py`) from a model that is simply too weak. A pipeline fault is fixed by PR and the same checkpoint is re-evaluated (an amendment records it; the pass bar does not change). If the model is too weak, the next options go to the user, each with its cost from the sizing basis:
  1. **More layers** (for example 16, then toward 30, as the mentor suggested increasing depth). At 16 layers the static memory roughly doubles from the sizing run's fitted 28.90 GiB for `none` (sizing LOG line 46), so it would not fit a 48 GB card under the fp32 recipe (speculative arithmetic); it needs an 80 GB card or a lighter precision recipe (Open item 8), and a new sizing measurement.
  2. **Longer training** (for example 20 epochs): about twice the 23.54 L40S-hours, same cards (arithmetic). The paper trains 10 epochs, so this is a departure from the paper.
  3. **A pretrained action expert:** Fast-WAM's resized-from-Wan recipe if the run used a fresh one (Open item 2); or start from Fast-WAM's released LIBERO checkpoint, which is 30 layers, a different model class (base and optional-IDM, action attends to the first frame only) and has no stated weights licence (`step2-reading.md` lines 70-77, 106), so it is a model-class decision, not a drop-in.
  4. **A different set of 8 blocks** (for example evenly spaced), the sizing PLAN's Open item 1 options (sizing PLAN lines 117-122).
  Any of these is a new run with its own PLAN or amendment and its own bar; none is started without the user's choice.

## Compute and cost
- **Where it runs: Open item 3.** The lead's recommendation is Nautilus 48 GB-class cards, with one paid L40S run as a fallback; the user has not decided.
- **Card-hours (sizing basis):** 21,696 steps x 3.907 s = 23.54 L40S-hours of training steps for `none` (sizing LOG line 41, verified). Not included: checkpoint writes, startup, data waits on CephFS, the sanity runs, failed or resumed runs, evaluation (sizing LOG line 41).
- **Step time on A40, RTX A6000 and L40 is not measured** (sizing LOG line 41, verified: "not transferred to A40/A6000/L40"). **How the first minutes settle it:** the training script logs seconds per optimizer step, data wait and peak memory from the first steps; after a short warm-up (for example 20 optimizer steps) the implementation session computes the projected training time (21,696 x the measured step time) and writes it in the experiment `LOG.md`. If the projection exceeds the time limit agreed at the go, the run is stopped and the user decides. The same first minutes show whether micro-batch 8 fits on that card. GPU use is checked about 15 minutes in (recalled lesson from earlier runs, not in a file read here).
- **Nautilus card access:** L40 and L40S are requested by `gpu.product`; A40 and RTX A6000 are NRP special resources (`nvidia.com/a40`, `nvidia.com/rtxa6000`) that a plain GPU request never reaches, and "A named-resource variant ... is added only with the user's OK" (proxy PLAN Amendment 2026-11-06 (b), lines 251-257, verified). Part of Open item 3.
- **NRP utilisation rule, as `STANDARDS.md` states it** (line 48, verified): utilisation above 40% of requested GPUs; requests and limits within 20% of each other; start on 1 GPU; NRP's portal emails the owner once a pod's average GPU use has been under 40% for about 3 h, admins can delete idle pods and that counts as a `gpu_idle` strike; the account is assumed to be at 1 of 3 strikes. Training at batch 128 on one card should keep the GPU busy (speculative; the proxy's A40 run showed 76 to 97%, proxy PLAN line 289); rollouts are the risk, handled as in "Evaluation time". **Gate:** more than 8 GPUs at once or more than 20 Jobs (line 49); this stage needs one training GPU and a few evaluation pods.
- **Paid compute rule** (`STANDARDS.md` lines 51-60, verified): the user's budget is about $30 a month, short jobs only, **long training stays on Nautilus**; no paid launch without the user's go in the launching session with the hourly price and estimated total stated first; estimated against actual dollars logged; paid resources stopped or deleted when the run ends. **A paid run of about a day is long training, so the paid fallback would need the user to set that rule aside for this run** (the worker's reading of the rule; the user's later words "okay so we know that paying for runs is actually feasible now", direction `LOG.md` line 1849, do not change the rule text). Prices read 2026-11-15 (sizing LOG lines 68-71, verified, prices move): one 23.54-hour L40S run is about $18.2 on Vast.ai at $0.774/h and about $18.6 on Runpod at $0.79/h, and $45.91 on Modal at $1.95/h (sizing LOG line 41). Not included: a paid provider needs the 31.4 GB VAE cache, T5 cache and meta files and the Wan shard copied off Nautilus and stored there (sizing LOG line 71; copies through `kubectl exec` broke at about 100 MB before and needed chunking with sha256 checks, sizing PLAN line 32, recalled there), and checkpoints of about 20 GB each need a volume that outlives the machine. These are priced on the day.
- **Evaluation cost:** not measured (see "Evaluation time").

## Hand-off
The implementation session (a lead with its own workers) does the following, code by PR, and **runs nothing on the cluster or a paid provider except on the user's own go in that session**:
- A training script beside `src/proxy_wam.py` that reuses its data, loader, loss, schedule and checkpoint code and `src/pretrained_sizing.py`'s build and `load_wan`, adds gradient accumulation (micro-batch flag, global batch 128) and a checkpoint interval, writes `model.pt` with a config `rollout.py` can load, and applies the user's choices on Open items 2, 7 and 8.
