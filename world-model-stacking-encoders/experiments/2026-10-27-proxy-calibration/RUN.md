## How the chaining works
- Submit a Job, then start `./watch_job.sh <job-name> <completions> 120` with the Bash tool's `run_in_background`. It polls the public Prometheus (no kubectl, so an expired login doesn't stop it) and exits on: 0 complete, 2 dead, 3 vanished, 4 a GPU pod idle below 40% (NRP floor), 5 never appeared, 6 a pod's CPU or RAM outside NRP's range (CPU 20–200% of request, RAM ≥ 20%; pods at the exempt size skipped). Its exit wakes you; then do the step's checks and move on. Don't poll in the foreground or add sleep loops.
- Run independent Jobs side by side when the GPU total stays ≤ 8.
- **kubectl login expires** after a few hours and then hangs (memory `nautilus-kubectl-auth-expiry`). Before every kubectl call that changes something, test it: `(kubectl get pods -n aria-world >/dev/null & pid=$!; sleep 25; kill $pid 2>/dev/null && echo HUNG)`. If it hangs, that's a stop: the user must run `! kubectl get pods -n aria-world` and log in. Jobs already running finish on their own meanwhile.
- After each step: append a short `[agent]` LOG entry (what ran, verified numbers, GPU-hours), commit. Keep every Job's log: `kubectl logs job/<name> > results/logs/<name>.log` within 24 h (TTL).

**Rollouts and the 40% GPU floor.** Simulator rollouts are mostly CPU (MuJoCo physics, rendering); the policy runs on the GPU only every 10 steps. One environment per GPU will very likely sit far below NRP's 40% (speculative until measured). So the rollout code (step 7) runs many environments per GPU process and batches their policy calls (or several rollout workers per pod sharing the GPU), with CPU requests sized for the simulators. Per-episode results must not depend on the batching (same episode, same eval seed → same initial state). The step 9 rollout Job must be timed **and** show ≥ 40% GPU over 10-minute windows (Prometheus `DCGM_FI_DEV_GPU_UTIL`) after startup; if it can't reach that by raising environments per GPU, stop and ask (stop 10) before any stage 4 rollouts.

## Stop conditions ("major problem")
Stop the chain, write a LOG entry, commit, and tell the user (use PushNotification if it's available, since they may be away) when any of these happens:
1. The same step fails twice (one diagnosed fix and retry is allowed; log the fix).
2. The watcher exits 4 (GPU idle) or 6 (CPU/RAM out of range) and the cause isn't an obvious, fixable startup phase (on 6, resize requests from Prometheus and resubmit; that counts as the one fix); or the NRP Violations page shows one of our pods (the user can check https://nrp.ai/userinfo).
3. kubectl login expired when a change is needed.
4. Orientation check (step 2) or the sim-vs-training frame check (step 8) shows a mismatch.
5. Measured costs blow past the plan: full extraction > 24 h wall, one training run > 48 h, the whole stage 4 > ~7 days, or anything that needs > 8 GPUs at once or > 20 Jobs.
6. A fix would need a change to configs, the outcome rule, the eval protocol, a design choice in PLAN, or the model size away from the default. Exception: the pilot may only *confirm* the default size; shrinking it is a stop.
7. The PVC is over 90% full, a Ceph mount hangs, or anything would need deleting data.
8. (Resolved 2026-10-28 (f): the threshold is locked in PLAN.) `lp_eval.py` doesn't implement the locked protocol when step 9 sizing or step 12 needs it.
9. Anything else that would make a reviewer question the result. When in doubt, stop.
10. Rollout Jobs can't keep the GPU at ≥ 40% (see "Rollouts and the 40% GPU floor").
A failed calibration (outcome rule 1) is a result, not a stop: finish the round, report it as the rule says.

**Step 7a. Analysis code to the locked protocol** (added 2026-10-28 (i); local, no cluster; do it while step 6 runs; must be done before step 9 sizing). PLAN "Pre-registered outcome rule" (incl. "Evaluation protocol" and "Sample-size rule") is the spec; implement it, never change it. In `src/lp_eval.py` + `src/test_lp_eval.py`:
1. `make_subset`: sample in proportion to each of the 28 suite × category cells' size in `task_classification.json` (total N, largest-remainder rounding, ≥ 1 per cell, one seeded generator); accept an exclusion list (the pilot episodes) and never draw from it. Remove equal per-cell allocation.
2. Eval seeds 41, 42, 43: every (config, train_seed) has exactly one record per subset episode × eval seed; fail loudly on missing, duplicate or extra rows. Per-episode score = mean success over the three eval seeds; all pairing uses these scores. Discordant counts = episodes where A scored lower / higher than B.
3. Verdict with the thresholds as named constants: calibration (a) D − none > 0 in all three train seeds and mean ≥ +2.7 points; (b) D+L − D mean ≥ −1.35. Fail → "don't interpret the D+R comparison from this proxy". Pass → D+R − D all three seeds < 0 and mean ≤ −2.7 → "substantial proxy effect (trigger for the higher-fidelity run, not statistical proof)", else "the proxy does not show a substantial effect". Always print each seed's value and the average, with the proxy-replication framing.
4. Sizing helper: from pilot records for `dinov3` and `dinov3+c-radiov4` (same train seed, same pilot episodes, eval seeds 41–43): sd of the paired per-episode difference after averaging the 3 eval seeds, sd* = 1.5 × sd, N = ceil((sd* / 1.35 points)²); print sd, sd*, N.
5. Any confidence interval resamples whole episodes (with their three rollouts together), never rollouts.
6. Synthetic tests with known answers: proportional allocation sums to N and matches cell shares; exclusion list respected; a missing eval seed is rejected; planted cases that pass calibration, fail (a), fail (b), and hit each D+R outcome, including the boundary values; sizing helper recovers a planted sd. All old and new tests pass.
Commit, log, and recreate the ConfigMap (step 3) before any Job uses the new `lp_eval.py`. Step 7's rollout writer must emit `eval_seed` and run each episode under all three seeds.
