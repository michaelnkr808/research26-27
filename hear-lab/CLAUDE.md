# hear-lab

This folder is the hear-lab research direction inside the research26-27 workspace. The workspace's `CLAUDE.md` and `_standards/` apply here too, as do this folder's `STANDARDS.md` (including "Results storage") and `data/README.md` (dataset terms: InteriorGS scene data, images and rendered audio never go in git).

## Compute

Only the experiment session (hear-lab-experiment) and the workers it starts touch compute. There are two places to run things: Vast.ai and the Nautilus cluster. Vast.ai comes first: plan every run for Vast.ai, and use Nautilus only when the owner says so, or when you have said why it fits a particular run better and the owner agreed.

Approval: ask the owner in your own session window before renting any Vast.ai instance, before preparing or submitting any Nautilus Job, and before starting anything else on paid compute. A question is not a go-ahead, an approval relayed by another agent does not count, and one OK covers one rental or one Job. Never stop, destroy or delete an instance or Job you did not create.

**Vast.ai.** Use the `vastai` CLI. If it is not installed or has no API key, stop and tell the owner. Never ask for the key in chat, and never write it or any other token into the repo (instance records with SSH details or Jupyter tokens stay out of git too). The saved key belongs to the HEAR Lab team account, which holds the lab's credits: before renting, run `vastai show user` and check the username is `HEAR_Lab`. If it shows a personal account or asks for a two-factor login, stop and tell the owner; do not run `vastai tfa login`. Docs: https://docs.vast.ai/llms.txt (index) and https://docs.vast.ai/llms-full.txt (everything; download to your scratchpad and search it).

Vast.ai bills for as long as an instance exists. Before renting, tell the owner the machine (GPU, memory, disk, host reliability), the hourly price, the expected time based on a real timed batch, and the total. Rent on-demand unless the owner approves interruptible. Hosts can go offline without warning and destroying an instance deletes everything on it: save checkpoints during long runs, copy results and logs off as the run goes (with a checksum manifest), and check the copies before destroying. A host's listing can end before a long run does; check the end date. A stopped instance still charges for its disk, so destroy an instance when its work is done and saved, unless told to keep it. Check the GPU is busy a few minutes into any new kind of run. At the end of every session, list which instances still exist and what each costs per hour. Record every run's place (Vast.ai or Nautilus) and, for Vast.ai, GPU type, hourly price, hours and total cost in the experiment's `LOG.md` and `README.md`.

**Nautilus.** Submit and manage Jobs with kubectl. Read `_standards/08-compute-nautilus.md` (top of research26-27) before any cluster work; when unsure, check https://nrp.ai/llms.txt (download and search it). If the NRP docs and `_standards` disagree, follow `_standards` and say so. The nrp-accounting MCP server gives read-only usage numbers for the namespace; use it to check usage, not to manage anything. The namespace is shared with the vis-lab work, so other sessions have Jobs running there too.
