## Check 1: does the sound engine run, and does the geometry line up (unknowns 1 and 2)

**Design.**
- Engine: the bare RLR-Audio-Propagation library at pinned commit `4fd446b` (github.com/facebookresearch/rlr-audio-propagation), `libRLRAudioPropagation.so` loaded through a ctypes binding written against its C header. No habitat-sim, no SoundSpaces Python code.
- Machine: a rented Linux x64 machine on Vast.ai (the library ships Linux x64 binaries only).
- Geometry: walls extruded from one real InteriorGS scene's `structure.json` (door and window openings left open), a floor and a ceiling per room, furniture as boxes from `labels.json`. Materials from RLR's shipped `mp3d_material_config.json` by label substring; anything unmatched gets the config's default. The material map is "assumed materials" and is written to the results.
- One source (at the box centre of the goal object of one real GN-Matrix episode in that scene) and one listener (at that episode's start pose, height 1.3 m, heading from the episode). Write one one-channel (mono listener) and one two-ear (binaural, the library's default HRTF) impulse response as WAV files, 44100 Hz (the library default).
- Settings: run the same source and listener twice and write both, so that the choice stays open: (a) the bare library defaults (transmission on, 5000 indirect rays, diffraction on, max diffraction order 10; header lines 118 to 154 at `4fd446b`), and (b) SoundSpaces' continuous simulator settings (transmission on, 500 indirect rays; `soundspaces/continuous_simulator.py` lines 123 and 125 at `287184f`). Every setting passed to the library is logged with the output. Thread count and wall time per impulse response are logged for both.
- Floor plan overlay: for four InteriorGS scenes (the scene above plus three others that appear in the GN-Matrix test_unseen split, chosen by sorted scene id with a fixed seed of 20261120), draw the `structure.json` walls onto that scene's `occupancy.png` through GN-Bench's own world-to-pixel mapping (from `occupancy.json`, the same code path the simulator uses), save the four overlay images, and compute one number per scene: the share of points sampled every 5 cm along wall centre lines that land within 2 pixels of an occupied pixel.
- Same run, unknown 3: look up every `label_ins_id` of the four scenes' GN-Matrix episodes in that scene's `labels.json` and count misses.

**Pass (before running).** Check 1 passes if all hold: the library loads and returns finite, non-zero impulse responses; mono has one channel and binaural two; the first arrival in the mono response lies within 1 ms of straight-line distance / 343 m/s when the source is in line of sight (if the chosen episode's source is not in line of sight, a second listener placement in line of sight is added for this test); for a source placed 2 m to the listener's left in open floor, the left ear's first arrival comes before the right ear's; the four overlays line up by eye (walls on occupancy borders, no flip, no scale or offset error) and the wall share is at least 0.9 in each scene. Any failure is reported with the error and the overlay images, and work stops for the lead before checks 2 and 3 spend money (the hand-off's stop rule). Fixable misalignments (a constant offset, a flip) are reported as such; fixing them is not done without the lead's OK, since the route A memo's fallbacks are the lead's call.

**Prediction:** I expect the library to load (`speculative`: it is archived since 2022 and its binary may need an older glibc). I have no expectation on the overlay.

## Check 3: how many starts have the target visible (unknown 4)

**Design.**
- Episodes: the full GN-Matrix `InteriorGS_test_unseen` split and a random sample of 1,000 episodes of `InteriorGS_train_seen` (numpy default_rng, seed 20261120, sampled without replacement by row). GN-Matrix and InteriorGS at the revisions downloaded, hashes recorded.
- At each episode's start pose (position, heading, camera height 1.3 m), render the depth image with GN-Bench's own simulator (`get_observations_at`, the episode's own world-to-splat transform) using the InteriorGS config's camera: 480 by 360, 70 degree horizontal field of view.
- Target box: the goal instance's oriented box from `labels.json`, found by `label_ins_id`. Episodes whose id is missing are counted and reported, not dropped silently.
- Proposed visibility rule (for this count only; the rule for the paper is set later in the experiment PLAN for the three-version comparison): sample points on the box surface on a grid of at most 5 cm spacing; project each into the image with the camera's pinhole intrinsics; a point is seen if it falls inside the image, lies in front of the camera, and its depth is at most the rendered depth at that pixel plus 0.15 m. The target is visible at the start if at least one point is seen. Also written per episode: the number of seen points, the share of the box's sampled points that are seen, and the result with tolerances 0.05 m and 0.30 m, so that a stricter or looser rule can be read off later without re-rendering.
- Also per episode: the start-to-goal straight-line distance and the geodesic path length from the GN-Matrix path, and a flag for starts within the 3.0 m success radius (`SUCCESS_DISTANCE`).

**Output:** one CSV per split with the flags above, and a summary of counts per split: visible, not visible, missing id, and how many of each start within 3.0 m. Ten start images (RGB and depth with the projected box drawn) per split are saved for a by-eye check of the rule.

**Pass (before running):** the counts are produced for both splits, and the saved images agree with the flag by eye in at least 9 of 10 per split. There is no target count; the counts are what the check reports.

**Prediction:** `speculative`, I expect most GN-Matrix starts to have the target out of view, since starts were not chosen for visibility.

## Amendments

### 2026-11-20: corrections found while writing the code, before any run on a rented machine

Seen so far: only local numbers from one InteriorGS scene (`0001_839920`, its small files on the experiment lead's Mac), computed by the workers' unit tests. No rented machine, no audio, no render. Stated here so that nothing is decided after the real results.

1. **Camera field of view.** GN-Bench uses the config's `HFOV` value 70 as the vertical field of view (`GN_Bench_simulator.py`, `fovy = math.radians(fov)`, GN-Bench-Tools `0ce8367`), so the 480 by 360 image is 70 degrees tall and about 86 degrees wide. The design above said "70 degree horizontal". Check 3 uses the camera the simulator actually renders; the design is otherwise unchanged.
2. **"Occupied" in the wall share was not defined above.** The code reads it as occupancy value 0 (the InteriorGS card's occupied value) and also reports GN-Bench's own notion (pixel value below 200, not passable). On `0001_839920` the local numbers were 0.87 (value 0) and 0.97 (not passable). The 0.9 bar stays on the value-0 share as first written. Both numbers are reported for all four scenes with the overlay images, and whether a value-0 miss is a real misalignment (for example the grey unknown border around outer walls) is left to the lead from the images. The bar is not changed after the fact.
3. **Goal position against goal object.** In `0001_839920` the GN-Matrix goal position is a median of about 5 m from the goal instance's box (9 or 10 of 38 episodes within 3 m, depending on which worker's distance measure). Check 3 adds a per-episode column `goal_to_box_horiz_m` and reports its distribution, since it bears on placing the sound at the goal object. No rule depends on it in these checks.
4. **"Within 3.0 m".** Check 3 writes both a path-length flag and a straight-line flag and reports both. GN-Bench's own success test uses a geodesic distance; neither flag is that exact quantity.
5. **Outputs stay out of git** until the InteriorGS terms (a PDF linked from the dataset card, not yet read) have been read: `results/.gitignore` ignores everything the runs write. Summaries of counts are committed only after the lead clears it.

### 4. Launcher and the settings that differ

The released command for training from a checkpoint is the stage II launcher with `INTERIORGS_DATA_ROOT`, `PRETRAINED_MODEL_PATH` and `OUTPUT_DIR` set (`docs/TRAINING.md` lines 152 to 160; `scripts/train/wnm_3d_stage2.sh`, which exports defaults and calls `wnm_3d_base.sh`). Check 2 runs, from the WNM-3D root:

```
NUM_GPUS=1 PER_DEVICE_BS=<12, or the search value> \
MAX_STEPS=60 SAVE_STRATEGY=no SEED=20261120 AUTO_DOWNLOAD_WEIGHTS=false \
PYTHONPATH=/workspace/check2/src/check2 \
INTERIORGS_DATA_ROOT=data/interiorgs_lerobot_check2 \
PRETRAINED_MODEL_PATH=checkpoints/wnm_3d_stage3_release \
VGGT_OMEGA_CKPT=checkpoints/vggt_omega_1b_512.pt \
OUTPUT_DIR=/workspace/check2/runs/<trial_id> \
bash scripts/train/wnm_3d_stage2.sh \
  2>&1 | <timestamp each line> | tee /workspace/check2/runs/<trial_id>.log
```

First the same command with `DRY_RUN=true` prints the full `torch.distributed.run` command with every Hydra argument (launcher lines 258 to 262); that text is saved and its settings are checked against the list below before the real run.

Settings that differ from the documented recipe (8 GPUs, per-device batch 12, ZeRO-2, bf16, 33 frames at 320 by 160; launcher lines 37 to 65 and 186 to 239), each with its reason:

1. `NUM_GPUS=1` (recipe 8, launcher line 37, stage II line 47). Reason: the user chose one H200.
2. Effective batch: `GLOBAL_BATCH_SIZE` is not set, so the launcher computes it as GPUs times per-device batch, 12 on one GPU at batch 12 (launcher line 43), and the trainer sets gradient accumulation to 1 (`gammanav/vln/experiment/base.py` lines 566 to 573, `gammanav/vln/experiment/utils.py` lines 75 to 80). Decided by the user 2026-11-20 ("Decided" item 1). The recipe's effective batch is 96 (8 GPUs by 12). What stays the same: the forward and backward work on the GPU per micro-batch of 12. What differs: each optimizer step here sees 12 samples, not 96, so the optimizer update (and its memory traffic for the whole optimizer state, which on one GPU is not sharded, see "Not claimed") runs 8 times as often per sample as in the recipe. Seconds per step here is therefore one micro-batch plus one optimizer update.
3. `PER_DEVICE_BS`: 12 as in the recipe; smaller only if 12 does not fit (search below).
4. `MAX_STEPS=60` (stage II default 70,000, line 49): warm-up plus timed steps (step 5). The cosine schedule and its 5 % warm-up (`WARMUP_RATIO` 0.05, launcher line 48) are then spread over 60 steps, so the learning rate values differ from a long run; this does not change the compute per step.
5. `LOGGING_STEPS` stays at the released 10 (launcher line 49). The first version of this amendment set it to 1 to get a timestamp per step; that is dropped (PR #77 review). Reason: the trainer's own step counter `current_step` counts micro-batches, not optimizer steps: it starts at 0 (`base.py` line 192) and is increased once per `training_step` call (line 220), which the Hugging Face trainer makes once per micro-batch. The metric interval is `logging_steps` (lines 199 to 206), and on micro-batches where `current_step` is a multiple of it the trainer runs `_collect_vggt_grad_metrics` (lines 215 to 218: a Python loop over all model parameters with a `.item()` per adapter gradient, lines 223 to 254) and the per-loss `.item()` logging (lines 262 to 287). With 1 that work would run on every micro-batch, an overhead of unmeasured size inside every timed step. Per-step timestamps come from the timing callback instead (step 5). Left as released and in the times: the `training_step_time` and `model_forward_time` log calls the trainer makes on every micro-batch (`base.py` lines 212 and 259, `timer.py` line 23), which the recipe also makes.

Batch-size search (each trial is a fresh launch with a fresh output folder):
- Start at 12. A trial "fits" only if all its optimizer steps finish; a CUDA out-of-memory error at any point means it does not fit.
- If 12 does not fit: try 8, 6, 4, 3, 2, 1 in that order and stop at the first that fits. That one gets the full timing protocol.
- If 12 fits: it gets the full timing protocol. Then try 16, then 24, each with 10 warm-up and 10 timed steps (`MAX_STEPS=20`), stopping at the first that does not fit. These answer "largest batch that fits" and are reported apart from the main timing.
- If even 1 does not fit with `zero2`: repeat the downward search from 12 with `DEEPSPEED_CFG=zero2_offload`, reported as a deviation. This fallback will most likely stop with a configuration error before any step. The run uses the Hugging Face `adamw_torch` optimizer (`conf.yaml` line 41; created in `base.py` lines 327 to 332), the transformers integration hands that client optimizer to DeepSpeed when the DeepSpeed config has no optimizer block (`integrations/deepspeed.py` lines 379 to 389, v4.51.3), and `zero2_offload.json` has neither an optimizer block nor `"zero_force_ds_cpu_optimizer": false`. DeepSpeed raises a `ZeRORuntimeException` ("You are using ZeRO-Offload with a client provided optimizer ...") when offload is on, the optimizer is not DeepSpeed's CPU Adam or CPU Lion, and `zero_force_ds_cpu_optimizer` is true, which is the default (`deepspeed/runtime/engine.py` lines 2415 to 2419 and `deepspeed/runtime/constants.py` lines 41 to 42, read at DeepSpeed v0.20.0, the latest release on PyPI on 2026-11-20; the version pip installs is unpinned and is recorded). WNM-3D's own comment at `base.py` lines 334 to 338 suggests the authors ran offload at some point, so this reading is `verified` for v0.20.0 only and not run. If the offload trial fails with this or any other optimizer or offload message rather than a CUDA out-of-memory error, it is reported as a configuration error, not as "does not fit", and work stops for the lead (adding `"zero_force_ds_cpu_optimizer": false` would be a change to a released config, which is the lead's call). If offload runs and still fails at batch 1 with out-of-memory, the result is "does not fit on one H200 with the released configs", reported with the error, and work stops.

### 5. Timing protocol

- Each full timing trial: 60 optimizer steps (`MAX_STEPS=60`), one micro-batch each (no accumulation); steps 1 to 10 are warm-up and excluded; steps 11 to 60 are timed (50 steps). The warm-up is meant to absorb `torch.compile`, CUDA graph capture and data loader start-up. All 60 step times are still written, so a slow warm-up that runs into the timed steps can be seen; the window is not moved after the fact.
- Timing and memory callback (`src/check2/`, not written yet; written and unit-tested on CPU before the rental, as its own reviewed change): a Hugging Face `TrainerCallback` that, at `on_train_begin` and at every `on_step_end` (once per optimizer step), calls `torch.cuda.synchronize()` and appends one JSON line with `global_step`, `time.time()`, `torch.cuda.memory_allocated()`, `torch.cuda.max_memory_allocated()`, `torch.cuda.memory_reserved()` and `torch.cuda.max_memory_reserved()` to `<OUTPUT_DIR>/check2_steps.jsonl`; it never resets the peak counters. It is attached without touching WNM-3D by a `sitecustomize.py` in `src/check2/` (that Python imports `sitecustomize` from `PYTHONPATH` at start-up, and that `torch.distributed.run` passes the environment to its worker, are `recalled`). `PYTHONPATH` reaches every Python process of the run (the `torch.distributed.run` parent, the training process, the data loader workers and the `torch.compile` worker processes), so the hook is lazy and guarded: `sitecustomize.py` imports neither `torch` nor `transformers` at top level; it installs only an import hook that, the first time `transformers.trainer` is imported, wraps `Trainer.__init__` to add the callback after the original `__init__` returns, and it does that only in the training process (`LOCAL_RANK` set in the environment); in every other process it does nothing. The callback added this way gets `on_step_end` once per optimizer step (with no accumulation, once per micro-batch; checked from the step numbers in the file). The first thing checked in each trial is that the file appears; if it does not, the trial is stopped and reported, not run without it.
- Cost of the callback: one `torch.cuda.synchronize()` per optimizer step (with no accumulation, once per micro-batch), four memory-counter reads and one JSON line. Not measured; expected small next to a step of several seconds (`speculative`); it is inside every reported time. The synchronisation also makes each timestamp a time at which the GPU work of that step has finished.
- Seconds per optimizer step: the differences between consecutive `on_step_end` times in `check2_steps.jsonl` (the first timed interval is measured from step 10 to step 11). Cross-check: the Hugging Face progress bar, which updates once per optimizer step (`recalled`), in the timestamped launcher log. The bar redraws with carriage returns, so the timestamping filter splits on carriage returns as well as newlines (for example `stdbuf -oL tr '\r' '\n'` before the timestamping step), giving one timestamped line per step. If the bar updates cannot be told apart in the log, the per-step times rest on the callback alone and the cross-check is the total wall time from the first to the last step in the log (not `train_runtime`, which includes warm-up and loading). A second, coarser cross-check: the wall-clock times of the `train/loss` TensorBoard scalar, which the trainer writes every 10 steps with `LOGGING_STEPS=10` (steps 10, 20, ..., 60), read with `tensorboard`'s event reader (a project dependency, `pyproject.toml` line 57). Reported: median, mean, minimum and maximum over the 50 timed steps, and all 60 values.
- Samples per second: per-device batch / median seconds per step (12 / median at batch 12).
- Per micro-batch: the trainer's own `training_step_time` log entries (`base.py` lines 211 to 213, `gammanav/vln/utils/timer.py` lines 15 to 23) are recorded, labelled approximate: they use `time.time()` without a CUDA synchronisation and leave out the optimizer step.
- Peak GPU memory: (a) torch, absolute: `max_memory_allocated` and `max_memory_reserved` in `check2_steps.jsonl`, read at two points, the `on_train_begin` line and the last step's line. The counters are never reset, so the value at `on_train_begin` is the peak of setup (model build and move to the GPU, DeepSpeed engine and optimizer-state allocation) and the final value is the peak since process start. If the two are equal, the peak came from setup, not from a training step, and is reported as such; otherwise the final value is reported as "peak since process start, including setup", next to the setup peak; (b) `nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used,memory.total,power.draw --format=csv -l 1` running beside the trial, written to `<trial_id>.nvidia-smi.csv`, maximum of `memory.used`. Both reported, with their labels (the `nvidia-smi` figure includes the CUDA context and the allocator's cache).
- GPU utilisation: the mean of the `nvidia-smi` samples over the timed window, and one look by hand 3 minutes after the first step is logged (if the timed window ends before that, the CSV alone is used and this is said). If utilisation sits near zero while steps are slow, that is reported (it would point at data loading or CPU work); it is not fixed during this check.
- Also recorded: the trainer's end metrics (`train_runtime`, `train_samples_per_second`, `train_steps_per_second`), labelled as including warm-up and model loading; the time from launch to the first logged step (model load plus compile); the gradient accumulation line the trainer prints (`base.py` lines 571 to 573); `loss_log.jsonl`; `trainer_state.json`; `experiment_cfg/conf.yaml`; the trainer's "train dataset length" and "train dataloader length" lines (`base.py` lines 613 to 617), to see whether 60 steps of 12 samples wrap around the 48-episode dataset (wrapping changes the order of samples, not the compute per step); the minutes the final model save takes (after the timed steps, `base.py` lines 621 to 627, not in any timing).
- Where logs go: `/workspace/check2/runs/<trial_id>/` and `/workspace/check2/runs/<trial_id>.log` on the machine; then step 6.
- Not claimed:
  - No loss or quality result: 60 steps of 12 samples on 48 episodes say nothing about learning. No training beyond the timed steps.
  - Nothing about the recipe's per-GPU step. ZeRO-2 on one GPU is not what each of the recipe's 8 GPUs does: on 8 GPUs each card holds and updates one eighth of the gradients and optimizer state and exchanges gradients with the others after each micro-batch; on one GPU there is no sharding (the whole optimizer state and the whole optimizer update sit on one card) and no communication, and the global batch is 12 instead of 96, so the optimizer update runs 8 times as often per sample. So "fits on one H200" implies the per-GPU memory of the 8-GPU recipe would also fit on such a card, but "does not fit on one H200" does not mean the 8-GPU recipe would not fit.
  - No speed claim for 8 GPUs. Samples per second on one GPU are not scaled to 8 GPUs as a speed figure. If a full-run cost is written next to the results, it is labelled arithmetic and built only for the one-GPU set-up measured here ("hours for N steps at the measured rate on one H200"), not for 8 GPUs.
  - Data loading. The 48 episodes (about 100 MB) sit on local disk and will be in the page cache after the first pass, so data loading is easier than in a real run on the full dataset; a loader bottleneck at 4 workers that a real run might hit would not show here.
  - The recipe's training hardware. Nothing cited documents the GPUs the authors trained on; the only hardware stated is an H100 80 GB for the inference server (`docs/INSTALLATION.md` lines 37 to 42). "The recipe" in this check means the launcher's defaults, not a known machine.

### 8. Open risks the user should know

- Driver: the cu129 PyTorch wheels need a host driver new enough for CUDA 12.9 (about 575 or later, `recalled`). Hosts with older drivers are filtered out; a mismatch shows as `CUDA available: False` in the install check.
- flash-attn: if pip cannot match the prebuilt wheel (for example a C++ ABI difference), it compiles from source, which can take an hour or more and a lot of RAM (`recalled`); `MAX_JOBS` is then set to limit parallel compile jobs. The 90-minute setup stop covers this. Without flash-attn the code silently falls back to PyTorch attention with the padding mask disabled (`attention.py` lines 215 to 242), which would no longer be the released path, so a missing flash-attn stops the run.
- DeepSpeed builds some of its CUDA ops on first use (`recalled`), which needs the conda CUDA 12.9 toolkit's `nvcc`; the offload fallback needs its CPU Adam op compiled.
- Memory: the checkpoint holds about 13.6 billion parameters (27.1 GB at 2 bytes each, arithmetic), of which the 5B-class DiT and the adapters are trained in full (`train_architecture=full`). With fp32 master weights and Adam state for the trained part, per-device batch 12 may not fit in 141 GB (`speculative`); the search handles this, and a "does not fit" is itself a result.
- CPU RAM: the model is first built on the CPU in fp32 (`model_dtype: float32`, `configs/model/wnm_3d/wnm_3d.yaml` line 15; `base.py` lines 499 to 531), about 54 GB by arithmetic, plus a 5 GB shard at a time; the offload fallback adds the optimizer state on the CPU. Hence the 192 GB RAM filter (`speculative`).
- Disk: about 51 GB of downloads, a conda env of roughly 15 to 20 GB (`speculative`), a final model save per trial (about 27 GB, deleted after each trial), the dataset (well under 1 GB). 300 GB leaves room (the full-repository downloads, about 168 GB more, are not done; decided 2026-11-20). A smaller disk would do; 300 GB is kept so that a missing-file stop can be followed by fetching the one missing file without resizing.
- Silent partial loading: the start weights are loaded with `strict=False` and the missing and unexpected keys are not printed (`base.py` lines 514 to 526). A key mismatch would go unnoticed; it would not change the timing much, but "started from stage 3" could not be confirmed from the trainer's logs. The start-weights key check (step 3, decided 2026-11-20) covers this.
- Compile warm-up: `torch.compile` with `dynamic=False` recompiles when an input shape changes (for example a short last batch); a recompile inside the timed window shows as an outlier step and is reported, not removed.
- Normalisation statistics are recomputed from the 48 episodes (`compute_statistics: true`, `configs/data/wnm_3d/interiorgs_wan22.yaml` line 138), as released. This changes the loss values, not the compute.
- The renders exist in one place only (the lead's scratchpad); see step 2.
- The stage 3 release's own `experiment_cfg/conf.yaml` records per-device batch 1, global batch 8 and 10 steps, which is not the documented recipe; this design follows the launcher and the guide, not that file.
